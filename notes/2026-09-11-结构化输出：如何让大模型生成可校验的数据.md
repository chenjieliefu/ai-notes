# 结构化输出：如何让大模型生成可校验的数据

> 日期：2026-09-11  
> 主题：JSON Schema、受约束解码、业务校验、失败恢复与安全边界

## 1. 什么是结构化输出

结构化输出是让大语言模型按照预先定义的数据结构返回结果，而不是只生成自由文本。

例如，从客服消息中提取信息时，不返回一段自然语言总结，而是返回：

~~~json
{
  "intent": "refund_request",
  "order_id": "A1024",
  "urgency": "normal",
  "missing_fields": []
}
~~~

结构化输出的价值不只是“看起来整齐”，而是让后续程序能够稳定解析、验证、存储和执行。

一个可靠方案通常包含四层：

1. 明确定义数据模式；
2. 在生成阶段约束语法；
3. 在应用层校验类型和业务规则；
4. 对失败、缺失与不确定性进行显式处理。

## 2. 为什么“请返回 JSON”还不够

### 2.1 模型生成的是 Token

语言模型根据概率逐 token 生成内容。即使提示中写了“严格返回 JSON”，它仍可能输出解释、Markdown 代码块、尾随逗号或不完整对象。

自然语言要求能提高遵循率，却不是语法保证。

### 2.2 语法正确不等于结构正确

下面内容是合法 JSON：

~~~json
{
  "amount": "很多",
  "currency": 100,
  "approved": "也许"
}
~~~

但如果模式要求 amount 为数字、currency 为货币代码、approved 为布尔值，它仍然不可用。

### 2.3 结构正确不等于业务正确

即使字段类型完全符合模式，模型也可能：

- 虚构订单号；
- 把小计当成总额；
- 选择不允许的退款原因；
- 生成不存在的来源链接；
- 把“不确定”错误地表示为 false；
- 给出越权操作参数。

因此，结构化输出解决的是接口可靠性的一部分，不是事实性和权限问题的全部。

## 3. 数据模式如何设计

### 3.1 字段名称要表达业务含义

字段名应稳定、明确，避免同时使用含义相近的名称，例如 status、state、result 混在同一对象中。

好的字段名让开发者、标注者和模型更容易理解同一概念。

### 3.2 类型要尽量精确

常见类型包括：

- 字符串；
- 数字；
- 布尔值；
- 数组；
- 对象；
- null；
- 枚举值。

如果字段只有有限取值，应使用枚举，而不是让模型自由生成相似表达。

例如 urgency 可以限定为：

~~~text
low | normal | high | critical
~~~

### 3.3 区分缺失、未知和不适用

这三种状态不同：

- **缺失**：输入本应提供，但没有提供；
- **未知**：存在信息，但无法可靠判断；
- **不适用**：该字段对当前情况没有意义。

可以使用 null、状态枚举或独立说明字段表达差异。不能把所有情况都填成空字符串。

### 3.4 必填与可选字段

必填字段适合每次都必须返回的核心结果；可选字段适合只在特定分支出现的信息。

模式过于宽松会让程序处理大量不确定形态；过于严格则可能迫使模型编造信息以填满必填字段。

### 3.5 版本化

模式一旦被下游系统使用，就成为接口契约。增加字段通常比删除或改变类型更安全，但仍要考虑旧客户端。

应记录 schema 版本，并让生产者和消费者明确支持范围。

## 4. JSON Schema 的作用

### 4.1 描述结构约束

JSON Schema 可以定义：

- 对象包含哪些字段；
- 哪些字段必填；
- 字段类型；
- 数值范围；
- 字符串格式；
- 数组元素结构；
- 枚举值；
- 是否允许额外字段；
- 条件和组合规则。

它为模型、应用和测试提供同一份机器可读契约。

### 4.2 关闭额外字段

如果下游只认识固定字段，可以禁止额外属性，减少模型擅自增加 explanation、confidence_reason 等内容。

但在模式演进阶段，完全禁止额外字段也可能降低兼容性，需要结合接口策略决定。

### 4.3 不要把复杂业务全塞进 Schema

模式适合表达结构和局部约束，却不适合承载所有业务逻辑。

例如“退款金额不得超过订单实付金额”需要查询订单系统并比较两个数据源，不能仅靠输出 schema 保证。

## 5. 受约束解码如何工作

### 5.1 基本思想

受约束解码会在模型生成每个 token 时，限制下一步只能选择仍可能形成合法结构的 token。

如果当前位置必须生成字段名，系统就屏蔽不符合语法的候选；如果枚举只允许三个值，也只开放能够组成这些值的 token 路径。

### 5.2 语法约束

系统可以把 JSON Schema、上下文无关文法或其他规则转换为生成约束。

这样能够防止括号不闭合、非法逗号和错误字段名等问题。

### 5.3 约束不是事后修补

事后修补是在模型输出无效 JSON 后尝试补括号或删除多余文字；受约束解码是在生成过程中阻止无效路径。

前者可能误改语义，后者更适合需要稳定接口的生产系统。

### 5.4 首次编译与缓存

复杂模式可能需要转换和编译为解码器可用的约束结构。首次使用可能有额外延迟，重复模式则可缓存。

频繁生成动态且不同的超复杂模式，会增加系统开销。

## 6. 语法保证的边界

### 6.1 可以保证什么

正确实现的约束解码通常能提高或保证：

- JSON 可解析；
- 字段符合允许集合；
- 类型结构正确；
- 必填字段存在；
- 枚举值合法；
- 不出现禁止的额外字段。

具体支持范围取决于模型服务和模式功能。

### 6.2 不能保证什么

它不能自动保证：

- 提取事实真实；
- 数字来自正确位置；
- 来源确实存在；
- 分类符合业务政策；
- 工具参数有权限；
- 高风险操作应该执行；
- 模型没有被提示注入影响。

模式保证“形状”，事实和行为仍需独立验证。

### 6.3 拒绝与截断

模型可能因为安全规则拒绝回答，也可能因长度、超时或连接中断而未完成输出。

应用不能看到部分 JSON 就当作完整成功，应检查生成状态和完成原因。

## 7. 业务校验为什么必须独立

### 7.1 类型校验

首先确认输出能被解析，并满足模式要求。即使服务宣称支持结构化输出，客户端仍应防御传输异常、版本差异和错误处理分支。

### 7.2 取值校验

对日期、金额、邮箱、订单号和资源标识使用确定性校验器。

正则表达式只能验证外形，例如订单号格式正确，不代表订单真实存在。

### 7.3 跨字段校验

字段之间可能存在关系：

- end_date 不得早于 start_date；
- tax + subtotal 应与 total 合理一致；
- action 为 refund 时必须提供 order_id；
- confidence 为 low 时不应自动执行高风险操作。

这些规则应由程序明确实现。

### 7.4 外部状态校验

模型生成的客户 ID、文件路径、收件人和库存数量必须到授权系统中核实。

任何涉及真实副作用的参数都要在工具执行前重新验证。

## 8. 如何表达不确定性

### 8.1 不要强迫模型猜值

如果输入缺失，模式却要求每个字段都有具体值，模型可能为了满足结构而编造。

可使用 null、unknown 枚举或 missing_fields 数组明确表示信息不足。

### 8.2 置信度不是概率保证

模型可以输出 confidence，但这个数值通常不是经过校准的真实正确概率。

比一个自由生成的百分比更有用的是：

- 证据片段；
- 来源位置；
- 缺失字段；
- 决策状态；
- 是否需要人工复核。

### 8.3 证据与结论分离

结构中可以分别保存：

~~~json
{
  "decision": "needs_review",
  "evidence": [
    {
      "source": "invoice_page_1",
      "text": "Total: 128.00"
    }
  ],
  "missing_fields": ["currency"]
}
~~~

应用仍需确认引用片段真实存在，不能因为模型输出了 evidence 字段就自动信任。

## 9. 实际例子：合同关键条款提取

一家企业希望从合同中提取签约方、起止日期、付款周期、自动续约、解约通知期限和责任上限。

### 9.1 模式设计

可以定义：

- parties：签约方数组；
- effective_date：日期或 null；
- termination_notice_days：整数或 null；
- auto_renewal：yes、no、unclear；
- liability_cap：金额对象或 null；
- evidence：每个结论对应的页码和原文；
- missing_or_ambiguous：无法确认的字段列表；
- review_required：是否需要法务复核。

### 9.2 生成阶段

模型根据合同文本和模式生成对象。受约束解码确保字段与类型合法。

对长合同应保留页码、段落和文档版本，避免只把脱离位置的文本块交给模型。

### 9.3 应用层校验

系统检查：

1. 日期格式是否有效；
2. 页码是否存在；
3. 证据原文能否在对应页面找到；
4. 金额和币种是否完整；
5. 自动续约与通知期限是否存在逻辑冲突；
6. 关键字段缺失时是否触发法务复核。

### 9.4 不能自动做的决定

即使结构完整，系统也不应直接认定合同风险“可接受”。条款解释可能依赖司法辖区、定义章节和其他交叉引用。

结构化提取可以辅助审查，不能替代律师的专业判断与组织授权。

## 10. 失败恢复与重试

### 10.1 先判断失败类型

失败可能来自：

- JSON 或 schema 不合法；
- 输出被截断；
- 模型拒绝；
- 业务规则不通过；
- 来源证据缺失；
- 外部系统查询失败；
- 网络超时；
- 模型服务不可用。

不同失败需要不同处理，不能全部用同一句提示重试。

### 10.2 有限重试

对于暂时性网络错误或格式异常，可以重试，但要设置次数和退避。

高风险操作不能因为模型未返回成功而盲目重复执行，必须使用幂等键或先查询真实状态。

### 10.3 修复重试

如果输出只违反局部业务规则，可以把明确错误反馈给模型，例如“end_date 早于 start_date，请重新检查证据”。

不要把含有秘密的完整内部错误栈直接放回模型上下文。

### 10.4 安全回退

持续失败时可以：

- 返回结构化错误；
- 请求用户补充字段；
- 转人工处理；
- 降级为只读摘要；
- 停止执行副作用操作。

可靠系统要能明确失败，而不是为了保持流程顺畅生成看似有效的数据。

## 11. 工具调用与结构化输出

### 11.1 工具参数也是结构化数据

模型调用工具时通常生成函数名和参数对象。模式约束可以确保参数结构正确，但不能判断调用意图是否被授权。

### 11.2 参数必须重新校验

执行器应检查：

- 工具是否在当前任务允许列表；
- 用户是否有权限；
- 资源 ID 是否属于允许范围；
- 收件人和网址是否可信；
- 金额和数量是否超过阈值；
- 是否需要确认；
- 操作是否可撤销。

### 11.3 读取与写入分离

模型可以先用结构化输出生成操作计划，再由应用展示给用户或交给受限执行器。

不要让一个“action”字段自动拥有执行权。

### 11.4 防范提示注入

外部文档可能诱导模型构造危险参数。即使参数完全符合 schema，数据流和权限仍可能违规。

因此，结构化输出是工具安全的必要组件之一，但不是完整安全边界。

## 12. 如何评估结构化输出系统

### 12.1 结构指标

- JSON 解析成功率；
- Schema 通过率；
- 必填字段完整率；
- 非法枚举比例；
- 额外字段比例；
- 截断率。

### 12.2 语义指标

- 字段级准确率、精确率和召回率；
- 完整对象完全匹配率；
- 数字、日期和实体提取准确率；
- 证据与结论一致率；
- 未知与缺失状态判断准确率。

### 12.3 业务指标

- 自动处理成功率；
- 人工修正率；
- 严重错误率；
- 错误执行和越权调用率；
- 每个任务的延迟与成本；
- 用户完成任务所需时间。

### 12.4 边界测试

测试集应包含：

- 缺少字段；
- 冲突信息；
- 多个候选实体；
- 无效日期和极端数值；
- 多语言与乱码；
- 超长输入；
- 模型拒绝；
- 提示注入；
- 网络中断和重复请求；
- Schema 版本不兼容。

## 13. 局限、风险与常见失败模式

### 13.1 把合法 JSON 当成正确答案

结构完全合法也可能包含幻觉、错误分类和虚假来源。

### 13.2 Schema 过于宽松

大量自由字符串和可选字段会把不确定性推给下游，使结构化输出失去契约价值。

### 13.3 Schema 过于严格

如果没有未知或缺失状态，模型会被迫猜测；复杂嵌套也可能增加延迟和失败率。

### 13.4 使用字符串承载所有类型

把日期、金额、布尔和枚举都定义成字符串，会让下游反复解析，并引入多种表示。

### 13.5 自动修复掩盖问题

静默补括号、猜字段或转换值可能让错误数据进入业务系统。修复必须可观察、可验证。

### 13.6 无限重试

模型持续失败时反复调用会增加成本和延迟，还可能重复副作用。重试要有限且幂等。

### 13.7 模式升级破坏兼容性

删除字段、改变类型或重命名枚举会让旧客户端失败。模式必须版本化并做兼容测试。

### 13.8 忽略拒绝与部分输出

模型拒绝、超时或被截断时，应用若强行解析已有片段，可能误判为成功。

### 13.9 让模型决定权限

结构化的工具调用仍然只是建议。授权必须由模型之外的系统判断。

## 14. 一套可落地的实践顺序

1. 明确下游真正需要哪些字段；
2. 为字段选择精确类型和枚举；
3. 设计缺失、未知和不适用状态；
4. 使用机器可读 schema 作为接口契约；
5. 能使用受约束解码时，不只依赖提示词；
6. 在客户端再次执行结构和类型校验；
7. 用程序实现跨字段与业务规则；
8. 对资源 ID 和事实查询授权系统；
9. 要求关键结论附带可验证证据；
10. 区分格式失败、事实失败和工具失败；
11. 设置有限、幂等的重试与安全回退；
12. 版本化 schema、提示、模型和评估集；
13. 上线后同时监控结构、语义和业务指标；
14. 高风险决策保留人工复核与权限控制。

## 15. 与其他 AI 方法的关系

### 15.1 与提示工程

提示工程说明任务、字段语义和边界；受约束解码提供语法层保证。两者互补，不能互相替代。

### 15.2 与 RAG

RAG 提供外部证据，结构化输出可以保存来源、页码和字段结论。应用仍要验证引用真实存在。

### 15.3 与 AI Agent

Agent 依靠结构化工具参数连接外部系统。结构正确只是第一关，还必须经过权限、数据流和副作用确认。

### 15.4 与 AI 评估

结构化输出让自动评估更容易，但应同时测量字段语义和最终任务成功率，而不只是解析率。

### 15.5 与微调

如果固定结构和领域分类长期稳定，微调可能提高遵循率和语义准确性；但模式变化频繁时，推理期 schema 通常更易维护。

## 16. 关键结论

1. 结构化输出把模型结果变成可解析、可校验的接口数据。
2. “请返回 JSON”是自然语言要求，不能提供可靠语法保证。
3. JSON Schema 可定义字段、类型、枚举和必填规则，是生产者与消费者的契约。
4. 受约束解码在生成阶段限制合法 token 路径，比事后修补更可靠。
5. 语法正确不代表事实、业务和权限正确，应用层校验不可省略。
6. 模式应显式表示缺失、未知与不适用，避免迫使模型编造。
7. 关键结论应附带证据位置，证据本身也要核验。
8. 工具参数即使符合 schema，也必须经过授权、范围和数据流检查。
9. 失败恢复要区分原因，重试必须有限、可观察且幂等。
10. 评估应同时覆盖结构通过率、字段准确率和端到端任务成功率。

## 17. 延伸思考

- 哪些业务约束适合写进 schema，哪些必须放在确定性程序中？
- 当模型无法确定字段时，怎样设计结构才能既诚实又便于下游处理？
- Schema 越严格是否一定越可靠，它会不会增加拒绝和延迟？
- 如何验证模型输出的证据引用确实支持对应结论？
- 当多个系统使用不同 schema 版本时，怎样设计安全的迁移与兼容策略？
