# Tokenization：大模型如何把文本切成可计算单元

> 日期：2026-08-27  
> 主题：子词切分、词表、Token ID 与上下文成本

## 1. 什么是 Tokenization

Tokenization（分词或标记化）是把原始文本转换成一串离散单元的过程，这些单元称为 token。大语言模型不能直接读取字符串，它实际接收的是 token 对应的整数编号。

一条文本进入模型时，通常经历：

1. 文本规范化；
2. 按 tokenizer 规则切分为 token；
3. 将每个 token 映射为词表中的 ID；
4. 将 ID 转换为向量表示；
5. 由 Transformer 处理这些向量。

模型生成文本时则反向进行：先预测下一个 token ID，再由 tokenizer 解码成人类可读的字符串。

## 2. Token 不等于汉字、单词或字节

### 2.1 为什么不直接按单词切分

如果把每个完整单词都放进词表，会遇到两个问题：

- 词表会因新词、变形和专有名词无限膨胀；
- 未见过的词无法表示，容易变成未知标记。

例如英文中的 connect、connected、connection 共享部分结构。把它们拆成可复用的子词，可以用有限词表组合出大量词语。

### 2.2 为什么不总是按字符切分

字符词表较小，几乎不会遇到未知字符，但序列会变长。序列越长，模型需要处理的步骤越多，上下文、延迟和计算成本也会增加。

### 2.3 子词是常见折中

现代大模型通常使用子词 token：高频词或片段保留为一个 token，低频词拆成多个更小单元。这样既能控制词表大小，又能表示新词。

必须注意，token 边界由具体 tokenizer 决定。同一句话在不同模型中可能被切成完全不同的序列，不能用“一个汉字等于一个 token”之类的固定规则估算。

## 3. Tokenizer 的基本组成

### 3.1 文本规范化

规范化可能处理 Unicode 形式、大小写、空白或特殊字符。是否执行以及如何执行取决于 tokenizer。

规范化可以减少表面差异，但也可能丢失信息。例如，在区分大小写的代码、产品型号或专有名词中，强制转小写会改变含义。

### 3.2 预切分

预切分先按空格、标点、字节边界或语言规则把文本分成候选片段。某些 tokenizer 会把单词前的空格编码进 token，因此同一个词出现在句首和句中时，token 可能不同。

### 3.3 子词模型

子词算法根据训练语料学习哪些片段值得进入词表。高频组合往往成为单独 token，罕见字符串则被拆成更细的片段。

### 3.4 词表与 Token ID

词表为每个 token 分配唯一整数 ID。ID 只是索引，本身没有“数字越大语义越复杂”的含义。

同一个 ID 在不同 tokenizer 中可能代表完全不同的文本，因此模型权重与 tokenizer 必须配套使用。错配会让输入含义彻底混乱。

## 4. BPE 如何学习子词

### 4.1 基本思想

Byte Pair Encoding（BPE）的常见做法是从较小单位开始，反复把训练语料中频繁相邻的片段合并，直到达到目标词表大小。

概念上可以想象：

1. 初始把词拆成字符或字节；
2. 统计相邻片段出现频率；
3. 合并最高频的一对；
4. 更新统计并继续；
5. 保存合并规则。

如果“人工智能”在训练语料中经常出现，算法可能逐步学到“人工”“智能”甚至整个词组；罕见组合则保持更细切分。

### 4.2 字节级 BPE

字节级 BPE 从 UTF-8 字节出发，理论上可以表示任意文本，不必为未知字符设置统一的未知 token。这对多语言、表情符号、代码和异常字符很有用。

代价是某些字符可能被拆成多个字节 token，序列效率会因语言和字符类型而不同。

### 4.3 BPE 的局限

BPE 优化的是语料中的统计频率，不是语言学意义上的词素。它可能在不直观的位置切分，也可能把训练语料中的偶然模式固化进词表。

## 5. Unigram 与 SentencePiece

### 5.1 Unigram 模型

Unigram 方法先准备较大的候选子词集合，再逐步删除对语料似然贡献较小的 token。编码时可以在多种切分方案中选择概率较高的一种。

与按合并规则构造词表的 BPE 不同，Unigram 把切分看成从候选子词中选择组合的问题。

### 5.2 SentencePiece

SentencePiece 是一种直接在原始文本上训练和编码的工具体系，可以实现 BPE 或 Unigram 等算法。它通常把空格也作为可编码符号，使处理不依赖传统的空格分词，适合中文、日文等没有天然空格边界的文本。

算法名称、实现方式和训练配置共同决定最终 tokenizer，不能只看到“BPE”或“SentencePiece”就推断所有细节。

## 6. 特殊 Token

模型词表中通常还包含具有控制作用的特殊 token，例如：

- 序列开始与结束；
- 消息角色边界；
- 填充位置；
- 工具调用或结构化数据边界；
- 图像、音频等多模态占位符。

特殊 token 由模型协议定义，不应随意手写或假设其字符串形式。聊天接口看到的 system、user、assistant 消息，进入模型前往往会通过聊天模板转换成包含特殊 token 的序列。

如果模板与模型不匹配，可能出现角色混淆、异常续写或停止条件失效。

## 7. Token、Embedding 与注意力的关系

### 7.1 Tokenization 负责离散表示

Tokenizer 只决定文本如何切分以及对应哪些 ID。它本身并不理解语义。

### 7.2 Embedding 负责向量表示

模型通过嵌入表把 token ID 映射为向量。训练过程中，语义和用法相近的 token 可能形成相关表示。

### 7.3 注意力负责组合上下文

Transformer 的注意力机制在序列中组合各 token 的信息。同一个 token 在不同上下文里会得到不同的上下文化表示。

因此，完整链路可以概括为：

文本 → token → ID → 初始向量 → 上下文化表示 → 下一个 token 概率。

## 8. 实际例子：一条混合语言的客服消息

假设用户输入：

“MacBook 到货了，但 USB-C 口无法充电 😢，order_id=AB-2048。”

### 8.1 可能的切分现象

具体切分取决于 tokenizer，但通常可能出现：

- 高频中文词被合并，也可能按单字或字节切分；
- MacBook、USB、order 等常见片段可能有独立 token；
- 连字符、下划线和等号可能单独占 token；
- AB-2048 可能被拆成字母、符号和数字片段；
- 表情符号可能是一个 token，也可能由多个字节 token 表示。

这说明肉眼看到的一句话，不等于模型看到的固定数量“词”。

### 8.2 对任务设计的影响

如果系统要提取订单号，不应假设订单号一定对应一个 token，也不应通过 token 位置硬编码规则。更可靠的方法是：

1. 让模型按结构化字段输出；
2. 用程序验证订单号格式；
3. 到业务系统确认订单号真实存在；
4. 对大小写、连字符和空格变体进行测试。

Tokenizer 负责表示文本，业务正确性仍要由应用层保证。

## 9. Token 对模型工程的影响

### 9.1 上下文窗口

模型的上下文限制通常按 token 数计算，而不是字符数。输入消息、系统提示、工具定义、检索资料、历史对话和输出都会占用预算。

当总长度超过限制时，系统可能截断内容。若关键规则或证据被截掉，回答会突然退化。因此需要明确的上下文组装与裁剪策略。

### 9.2 延迟与成本

许多模型服务按输入和输出 token 计费。更长的提示词不仅更贵，也可能增加首 token 延迟和总生成时间。

优化时应删除重复说明、压缩历史记录、只检索相关片段，并把稳定规则放在清晰位置，而不是单纯追求“提示词越长越好”。

### 9.3 生成停止条件

模型按 token 逐步生成。停止序列如果跨越多个 token，或与实际编码边界不一致，可能无法按预期触发。结构化输出应优先使用接口提供的模式约束和完成状态，而不是只依赖字符串截断。

### 9.4 训练数据效率

相同字符长度在不同语言中可能对应不同 token 数。tokenization 效率较低的语言会占用更多上下文和计算，影响训练覆盖、推理成本与用户体验。

## 10. 局限、风险与常见失败模式

### 10.1 用字符数估算 Token

字符数只能粗略参考，代码、数字、空白、表情和不同语言都会改变比例。准确预算应使用目标模型对应的 tokenizer 实际计算。

### 10.2 更换模型却沿用旧 Tokenizer

模型和 tokenizer 不匹配会产生错误 ID。迁移模型时必须一起迁移词表、特殊 token 和聊天模板。

### 10.3 忽略截断方向

简单地从头部或尾部截断可能删除系统规则、用户最新问题或关键证据。应按内容角色和重要性设计裁剪策略，并记录哪些部分被省略。

### 10.4 对罕见字符串处理不稳

序列号、哈希、URL、拼写错误和混合字符常被切得很碎。模型可能复制错误、漏字符或错误归一化。需要格式校验、工具查询和复制测试。

### 10.5 多语言效率不均

词表训练语料不均衡会使低资源语言切分更碎。平均英文指标不能代表其他语言，应分别测量 token 长度、质量、延迟和成本。

### 10.6 把 Token 当成完整语义单位

一个 token 可能只是词的一部分、一个空格或若干字节。解释模型时，不能把单个 token 机械等同于一个概念。

### 10.7 特殊 Token 使用错误

手工拼接角色标记或停止标记可能与官方模板冲突。应使用模型提供的标准 tokenizer 和消息模板，并对升级后的行为做回归测试。

## 11. 如何评估 Tokenizer 是否合适

可以从以下维度比较：

1. 词表大小与模型嵌入层成本；
2. 不同语言的平均每字符 token 数；
3. 代码、数字、URL 和领域术语的切分效率；
4. 任意 Unicode 文本是否可无损编码与解码；
5. 特殊 token 与聊天模板是否完整；
6. 对下游任务质量、延迟和成本的影响；
7. 训练语料与目标用户分布是否匹配。

Tokenizer 不能只按压缩率选择。词表过大增加模型参数，切分过细增加序列长度，最终需要结合模型和任务共同评估。

## 12. 关键结论

1. Tokenization 把文本转换为 token ID，是文本进入大模型的第一步。
2. Token 不等于固定的字、词或字节，边界由具体 tokenizer 决定。
3. 子词方法在词表大小、未知文本和序列长度之间取得折中。
4. BPE 通过频繁片段合并构造词表，Unigram 通过候选概率选择切分。
5. 模型、词表、特殊 token 和聊天模板必须配套使用。
6. Token 数直接影响上下文容量、延迟、成本和截断风险。
7. 多语言、代码和罕见字符串需要单独评估，不能依赖平均经验值。
