# 采样策略：大模型如何选择下一个 Token

> 日期：2026-09-16  
> 主题：大语言模型推理、解码策略与生成质量控制

## 1. 为什么“下一个 Token 怎么选”很重要

大语言模型生成文本时，并不是一次性写出完整答案，而是反复执行同一个过程：

1. 根据当前上下文计算下一个 Token 的概率分布；
2. 按某种解码策略选出一个 Token；
3. 把它追加到上下文；
4. 再预测下一个 Token，直到满足停止条件。

模型参数决定了“哪些 Token 看起来更可能”，采样策略决定了“最终选哪一个”。同一个模型、同一个提示词，仅改变温度、Top-k 或 Top-p，就可能得到风格、稳定性和事实准确率明显不同的输出。

因此，采样并不是一个无关紧要的随机开关，而是模型能力与产品行为之间的重要控制层。

## 2. 从 Logits 到概率分布

### 2.1 Logits 是什么

模型在每一步会为词表中的每个候选 Token 输出一个实数分数，通常称为 logits。分数越大，模型越倾向于选择该 Token，但 logits 本身还不是概率。

假设当前只考虑四个候选 Token：

| Token | Logit |
| --- | ---: |
| “北京” | 4.0 |
| “上海” | 2.5 |
| “中国” | 1.5 |
| “天气” | 0.5 |

### 2.2 Softmax 如何得到概率

Softmax 把 logits 转换为总和等于 1 的概率分布：

[
P_i = rac{e^{z_i}}{sum_j e^{z_j}}
]

其中，(z_i) 是第 (i) 个 Token 的 logit，(P_i) 是它被选中的基础概率。

Softmax 不会改变候选项的排序，但会把分数差异转换为概率差异。随后，解码器可以直接选择最高概率项，也可以从分布中随机抽样。

### 2.3 概率不是事实置信度

某个 Token 的生成概率高，只代表它在当前上下文和模型参数下更符合语言模式，不代表对应陈述一定真实。例如，模型可能高概率生成一个常见但错误的人名、日期或引用。

所以，生成概率不能替代事实核验，也不能直接当作业务系统里的可信度分数。

## 3. 两类基本解码方式

### 3.1 贪心解码

贪心解码每一步都选择概率最高的 Token：

[
y_t = argmax_i P(y_i mid y_{<t}, x)
]

它的优点是：

- 行为较稳定；
- 计算和理解都简单；
- 适合分类标签、字段提取等追求确定性的任务。

它的局限是：

- 局部最优不等于整段文本最优；
- 容易产生模板化、重复或过于保守的表达；
- 早期一步选错后，后续内容会沿错误上下文继续生成。

### 3.2 随机采样

随机采样按照概率分布抽取 Token。高概率 Token 更容易被选中，但低概率 Token 也有机会出现。

它能增加表达多样性，适合创意写作、头脑风暴和生成多个候选方案；但随机性过强时，也更容易引入跑题、矛盾、格式错误和事实偏差。

实际系统通常不会直接对完整词表做原始随机采样，而是先调整或截断概率分布，再进行抽样。

## 4. 温度：调整概率分布的陡峭程度

### 4.1 温度的基本原理

温度参数 (T) 通常作用于 logits：

[
P_i(T) = rac{e^{z_i/T}}{sum_j e^{z_j/T}}
]

- 当 (T < 1) 时，概率分布更尖锐，高概率 Token 的优势被放大；
- 当 (T > 1) 时，概率分布更平坦，低概率 Token 获得更多机会；
- 当 (T) 接近 0 时，行为通常趋近贪心选择，但具体接口可能会特殊处理 0；
- 当 (T = 1) 时，保留原始 Softmax 的相对尺度。

### 4.2 温度不是“创造力旋钮”的全部

把温度简单理解为创造力并不完整。温度直接改变的是候选 Token 的概率差异，创造性只是可能出现的结果。

高温度可能带来：

- 更多措辞变化；
- 更少见的联想；
- 更高的跑题和不一致概率；
- 更难保持严格格式。

低温度可能带来：

- 更一致的答案；
- 更稳定的结构；
- 更强的高频表达偏好；
- 多次生成结果过于相似。

### 4.3 温度不能修复知识缺口

如果模型没有可靠知识、上下文缺少证据，降低温度只会让模型更稳定地选择它认为最可能的答案，不会自动让答案变正确。

## 5. Top-k：只保留概率最高的 k 个候选

### 5.1 工作方式

Top-k 采样先按概率排序，只保留前 (k) 个 Token，把其余候选概率设为 0，再对保留项重新归一化并抽样。

例如，若 (k=3)，无论词表有多大，每一步最多只从三个候选 Token 中选择。

### 5.2 优点与局限

优点：

- 排除大量极低概率候选；
- 容易控制候选集合大小；
- 可减少离谱词语被采到的机会。

局限：

- 固定的 (k) 不会适应概率分布形状；
- 当模型非常确定时，保留 50 个候选可能过宽；
- 当多个候选都合理时，保留 3 个又可能过窄；
- 不同生成步骤适合的候选数量可能完全不同。

因此，Top-k 控制的是“数量”，而不是保留下来的总概率质量。

## 6. Top-p：按累计概率动态保留候选

### 6.1 核采样的原理

Top-p 也称 nucleus sampling。它从概率最高的 Token 开始累加，保留累计概率达到阈值 (p) 的最小候选集合，再在集合中抽样。

假设排序后的概率为：

| Token | 概率 | 累计概率 |
| --- | ---: | ---: |
| A | 0.55 | 0.55 |
| B | 0.25 | 0.80 |
| C | 0.12 | 0.92 |
| D | 0.05 | 0.97 |
| E | 0.03 | 1.00 |

当 (p=0.9) 时，候选集合通常会包含 A、B、C。由于每一步的分布不同，候选数量也会动态变化。

### 6.2 Top-p 的特点

- 模型很确定时，候选集合会自动缩小；
- 分布较平坦时，候选集合会自动扩大；
- 比固定 Top-k 更能适应不同上下文；
- (p) 越低，输出通常越集中和保守；
- (p) 越高，输出通常越多样，但尾部风险也会上升。

“累计概率达到阈值”的边界处理、是否至少保留一个 Token 等细节可能因推理框架而异。

## 7. 重复惩罚与频率控制

### 7.1 为什么模型会重复

自回归生成会把自己刚生成的内容继续作为上下文。某个词或句式一旦出现，就可能提高相似内容再次出现的概率，形成循环：

- 重复同一句话；
- 列表条目换词不换意；
- 长文本不断回到同一结论；
- 代码或标记无法正常闭合。

### 7.2 常见控制方式

不同平台的参数定义并不完全相同，常见思路包括：

- **重复惩罚**：降低已出现 Token 的分数；
- **频率惩罚**：出现次数越多，惩罚越大；
- **存在惩罚**：只要出现过就施加一次惩罚；
- **禁止词或 Logit Bias**：提升或压低指定 Token 的分数；
- **N-gram 限制**：禁止重复出现某些连续 Token 组合。

### 7.3 惩罚过强的副作用

技术文档、合同、代码和专有名词本来就需要重复。惩罚过强可能导致：

- 变量名被错误替换；
- 术语前后不一致；
- 为避免重复而使用生硬同义词；
- JSON 键名或固定模板发生变化。

重复控制应根据任务类型调整，不能只追求表面上的词汇多样性。

## 8. 停止条件：生成何时结束

常见停止条件包括：

1. 模型生成结束 Token；
2. 达到最大输出 Token 数；
3. 命中指定停止序列；
4. 结构化解码器确认完整对象已经闭合；
5. 应用层根据业务协议主动终止。

停止序列应谨慎设计。如果使用过于常见的文本作为停止标记，模型可能提前结束；如果最大长度过小，答案可能被截断在句子、代码块或 JSON 对象中间。

最大输出长度也不是“越大越好”。过大的上限会增加延迟、费用以及失控长输出的风险。

## 9. 多种参数如何组合

典型生成流程可以抽象为：

1. 模型计算 logits；
2. 应用禁止词、重复惩罚或其他 logit 变换；
3. 使用温度调整分布；
4. 使用 Top-k、Top-p 等规则截断候选；
5. 重新归一化概率；
6. 抽取下一个 Token；
7. 检查停止条件。

这只是概念流程。不同模型服务和推理框架可能采用不同顺序、默认值和边界规则，因此相同参数不保证跨平台得到相同结果。

实践中应记录模型版本、推理框架、随机种子、参数值和提示词版本，避免只保存一个“temperature=0.2”却无法复现完整环境。

## 10. 随机种子与可复现性

伪随机采样通常可以使用随机种子。相同种子有助于复现实验，但它不是绝对保证。

以下变化都可能让结果改变：

- 模型权重或服务版本更新；
- 分词器变化；
- 推理框架和采样实现变化；
- 浮点计算或并行调度差异；
- 提示词中的空格、顺序或隐藏系统指令变化；
- 工具返回内容或检索结果变化。

因此，种子适合用于调试和对比实验，不应被当作跨时间、跨平台的永久确定性承诺。

## 11. 实际例子：为客服回答和广告创意配置不同采样策略

### 11.1 场景 A：客服退款政策回答

目标是严格依据政策，稳定输出清晰步骤。可以采用偏保守的设置：

- 较低温度；
- 较窄的 Top-p 或直接使用确定性输出；
- 明确最大长度；
- 结构化输出或固定字段；
- 通过检索提供最新政策原文；
- 对金额、日期和资格条件做程序校验。

这里的重点不是“写得新颖”，而是证据一致、格式稳定和可审计。

### 11.2 场景 B：生成广告创意候选

目标是一次获得多种角度，再由人筛选。可以采用更开放的设置：

- 中等温度；
- 相对宽的 Top-p；
- 每次生成多个候选；
- 使用不同创意方向作为提示条件；
- 增加重复检测和品牌合规检查。

这里允许措辞多样，但仍需限制虚假承诺、敏感表达和品牌禁用词。

### 11.3 一组简化概率的对比

假设候选开头的概率为：

- “轻松”：0.45
- “立即”：0.25
- “重新”：0.15
- “探索”：0.10
- “突破”：0.05

偏保守策略会更频繁选择“轻松”；提高温度并放宽候选集合后，“探索”或“突破”更可能出现。这样能增加创意差异，同时也可能产生更夸张、需要审核的文案。

这个例子说明：没有全局最优的采样参数，只有与任务目标和风险边界更匹配的配置。

## 12. 如何系统调参

### 12.1 先定义任务目标

先回答以下问题：

- 输出是否必须可复现？
- 事实错误的成本有多高？
- 是否要求严格 JSON、代码或固定模板？
- 多样性是否能产生业务价值？
- 输出是否会直接触发外部操作？
- 是否有人或程序进行后验检查？

### 12.2 一次只改变少量变量

同时调整温度、Top-k、Top-p、提示词和模型，会让结果难以归因。更稳妥的方法是：

1. 固定模型、提示词和测试集；
2. 先建立基线配置；
3. 每轮只改变一个核心参数；
4. 多次采样，观察平均表现和波动；
5. 在质量、稳定性、延迟和成本之间选择折中点。

### 12.3 按任务建立预设

可以为不同任务维护独立预设，而不是让所有请求共享一组参数：

| 任务 | 采样倾向 | 重点 |
| --- | --- | --- |
| 信息抽取 | 保守 | 字段准确、格式合法 |
| 基于资料问答 | 较保守 | 引用一致、减少无依据扩写 |
| 代码生成 | 保守到中等 | 可运行、接口一致 |
| 摘要 | 较保守 | 覆盖重点、不添新事实 |
| 头脑风暴 | 中等到开放 | 多样性、角度差异 |
| 文学创作 | 开放 | 风格、意外性、连贯性 |

这些是实验起点，不是通用固定数值。最终参数应由具体模型和评测结果决定。

## 13. 如何评估采样配置

### 13.1 质量指标

根据任务选择指标，例如：

- 事实准确率；
- 引用或证据一致率；
- JSON Schema 通过率；
- 代码执行通过率；
- 指令遵循率；
- 人工偏好评分。

### 13.2 多样性指标

只看单次最佳结果会掩盖采样波动。应在同一输入上生成多次，评估：

- 不同答案占比；
- 词汇或语义重复度；
- 候选覆盖的观点数量；
- 最差结果的质量；
- 高风险错误出现频率。

### 13.3 稳定性指标

对轻微改写的提示词、不同长度上下文和边界输入进行测试，观察：

- 格式是否持续有效；
- 核心结论是否大幅漂移；
- 是否出现异常长输出；
- 是否频繁触发敏感或不合规内容；
- 参数改变后，收益是否稳定存在。

线上系统还应监测截断率、重试率、人工接管率和用户纠错率。

## 14. 局限、风险与常见失败模式

### 14.1 把低温度误当成事实保障

低温度提高的是选择一致性，不是知识真实性。缺少可靠证据时，模型可能稳定地产生同一个错误答案。

### 14.2 参数叠加导致分布过窄

同时使用很低的温度、很小的 Top-k 和很低的 Top-p，可能只剩极少候选，导致：

- 输出僵硬；
- 重复增多；
- 创意任务退化；
- 模型无法自然表达不确定性。

### 14.3 参数过宽导致尾部风险

高温度和宽候选集合会增加低概率 Token 的机会，可能带来：

- 事实错误；
- 格式破坏；
- 前后矛盾；
- 不恰当或不安全内容。

### 14.4 只优化平均质量

高风险应用不能只看平均分。即使 99 次表现很好，只要第 100 次可能输出危险指令或执行错误操作，就需要权限控制、规则校验和人工确认。

### 14.5 忽略模型与版本差异

一组参数在某个模型上有效，不代表迁移到另一个模型后仍然合适。服务升级后也应执行回归测试。

### 14.6 用采样参数解决提示词或数据问题

输出跑题可能来自任务描述不清，事实错误可能来自检索失败，格式错误可能需要受约束解码。仅靠不断调温度通常治标不治本。

## 15. 采样与其他技术的关系

### 15.1 与提示工程的关系

提示词定义任务和约束，采样控制在这些条件下如何选择 Token。清晰提示与合适采样需要配合：提示不清时，保守采样也可能稳定地产生错误理解。

### 15.2 与结构化输出的关系

严格结构更适合使用 JSON Schema、语法约束或工具调用协议。低温度可以辅助稳定，但不能替代结构校验。

### 15.3 与 RAG 的关系

RAG 提供外部证据，采样策略影响模型如何利用和表述证据。事实型问答通常偏保守，但仍需检查引用是否真正支持结论。

### 15.4 与安全治理的关系

采样参数只能改变某些错误出现的概率，不能构成完整安全边界。权限隔离、输入净化、输出校验、审计和人工确认仍然必要。

## 16. 一个可执行的配置流程

1. 明确任务的质量、风险和多样性目标；
2. 准备包含正常、边界和对抗样本的评测集；
3. 固定模型、提示词、检索数据和工具版本；
4. 从服务默认值或保守基线开始；
5. 对温度与 Top-p 做小范围网格实验；
6. 每个配置重复生成多次；
7. 同时统计平均表现、波动和最差结果；
8. 对严格格式增加结构校验，而不是只降温度；
9. 对高风险动作增加权限与人工确认；
10. 上线后持续记录参数、版本和失败案例；
11. 模型或服务更新时重新执行回归测试。

## 17. 关键结论

1. 大模型逐 Token 生成，采样策略决定每一步如何从概率分布中选择候选。
2. 温度调整概率分布的尖锐程度；Top-k 限制候选数量；Top-p 按累计概率动态限制候选集合。
3. 贪心或低随机性更稳定，但不保证事实正确；高随机性增加多样性，也扩大尾部风险。
4. 重复惩罚、停止条件和最大长度都会显著影响最终结果，且不同平台实现可能不同。
5. 没有适用于所有任务的最佳参数，应根据准确性、格式、多样性和风险要求分别配置。
6. 调参必须基于多次生成和任务评测，不能凭单个示例判断。
7. 采样参数不能替代 RAG、结构化约束、事实校验、权限控制或人工审核。

## 18. 延伸思考

可以继续思考以下问题：

- 是否能让系统根据任务风险自动选择采样预设？
- 如何用熵等统计量识别模型当前是“很确定”还是“候选分散”？
- 能否先开放采样生成多个方案，再用评审模型或规则选择最佳结果？
- 在 Agent 场景中，语言回复和工具调用是否应该使用不同采样策略？
- 当模型版本更新时，怎样自动发现采样参数已经不再适配？
- 除了温度与 Top-p，受约束解码和搜索算法如何进一步改变生成路径？
