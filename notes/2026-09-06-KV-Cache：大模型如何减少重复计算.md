# KV Cache：大模型如何减少重复计算

> 日期：2026-09-06  
> 主题：自回归生成、键值缓存、显存占用、批处理与长上下文推理

## 1. 什么是 KV Cache

KV Cache（Key-Value Cache，键值缓存）是大语言模型在自回归生成时保存历史注意力中间结果的机制。

大模型通常一次生成一个 token。生成第一个 token 后，第二步需要读取“原始输入 + 第一个 token”；第三步又要读取“原始输入 + 前两个 token”。如果每一步都重新计算全部历史 token 的注意力键和值，会产生大量重复工作。

KV Cache 的做法是：历史 token 的 Key 和 Value 计算一次后保存起来。下一步只计算新 token 的 Key、Value 和 Query，再让新 Query 与缓存中的历史 Key、Value 做注意力计算。

它不会让模型跳过历史上下文，而是避免重复生成已经算过的中间表示。

## 2. 为什么自回归生成会重复计算

### 2.1 Prefill 与 Decode

推理通常分成两个阶段：

1. **Prefill（预填充）**：一次处理系统提示、用户问题、检索资料等已有输入，建立首批 KV Cache；
2. **Decode（逐 token 解码）**：每一步加入一个新 token，复用历史缓存并生成下一个 token。

Prefill 适合较大的矩阵计算，通常更容易充分利用 GPU；Decode 每步处理的新增 token 很少，更容易受显存带宽、调度和通信影响。

### 2.2 没有缓存时会发生什么

假设输入有 1,000 个 token，模型要继续生成 200 个 token。

没有 KV Cache 时，每次生成都可能重新处理越来越长的完整序列：第 1 步处理约 1,000 个 token，第 200 步处理约 1,199 个 token。许多历史位置的 Key 和 Value 被反复计算。

使用 KV Cache 后，Prefill 先处理 1,000 个输入 token；之后每个 Decode 步骤主要为新 token 计算一次投影，再读取已有缓存。

### 2.3 为什么仍然会随上下文变慢

缓存消除了历史 Key、Value 的重复计算，但新 Query 仍需与全部可见历史 Key 计算注意力，并使用对应 Value 聚合输出。

因此，上下文越长，每一步需要读取的缓存越多。KV Cache 降低了重复计算，却没有把长上下文注意力变成常数成本。

## 3. Key、Value 和 Query 从哪里来

### 3.1 注意力投影

在 Transformer 的注意力层中，隐藏状态会经过不同线性变换得到：

- Query：当前 token 想寻找什么；
- Key：每个 token 可以被怎样匹配；
- Value：匹配后要取回的信息。

注意力可概念化为：

~~~text
Attention(Q, K, V) = softmax(QKᵀ / √d) V
~~~

实际模型还会使用多头注意力、位置编码、遮罩和优化内核。

### 3.2 为什么缓存 K 和 V，不缓存所有结果

生成新 token 时，新 Query 会变化，因此必须重新计算；历史 token 的 Key 和 Value 在模型权重、上下文与位置不变时保持不变，可以复用。

历史注意力的最终输出不能简单复用，因为新 token 的查询不同，关注历史位置的权重也不同。

### 3.3 每层都有自己的缓存

KV Cache 不是只有一份。Transformer 的每个注意力层都有独立的 Key 和 Value，通常还按批次、注意力头、序列位置和头维度组织。

因此，层数、序列长度、并发请求和数据精度都会影响缓存大小。

## 4. 增量解码如何工作

### 4.1 第一次处理输入

Prefill 阶段并行处理全部输入 token，为每一层生成历史 Key 和 Value，并保存到缓存中。最后一个位置的输出用于预测首个新 token。

### 4.2 生成新 token

在一次 Decode 步骤中：

1. 把刚生成的 token 输入模型；
2. 在每层计算该 token 的 Query、Key 和 Value；
3. 把新的 Key、Value追加到对应层缓存；
4. 用新 Query 读取可见的全部历史 Key、Value；
5. 计算下一个 token 的概率分布；
6. 选择 token 后进入下一步。

### 4.3 因果约束

自回归模型不能读取未来 token。因果遮罩确保当前位置只关注自身和之前的位置。

增量解码时缓存只包含已经出现的 token，天然符合时间顺序；但系统仍要正确维护位置编号和遮罩，尤其是在批处理、填充、滑动窗口或部分缓存复用时。

## 5. KV Cache 占多少显存

### 5.1 一个近似公式

对常见解码器模型，单个请求的 KV Cache 大小可粗略表示为：

~~~text
缓存字节数 ≈ 2 × 层数 × KV 头数 × 头维度 × 序列长度 × 每元素字节数
~~~

其中的 2 表示同时保存 Key 和 Value。

批量服务时，还要乘以同时驻留的请求数。不同架构、张量布局、对齐方式和推理框架会带来额外开销。

### 5.2 上下文长度线性影响容量

在其他条件不变时，序列长度翻倍，KV Cache 通常也近似翻倍。长上下文请求因此可能显著挤压并发容量。

一个模型的权重能够装入显存，不代表它能同时服务很多长对话；权重和运行时缓存是两类不同占用。

### 5.3 MHA、MQA 与 GQA

- **MHA（Multi-Head Attention）**：多个 Query 头通常各自拥有对应的 Key、Value 头；
- **MQA（Multi-Query Attention）**：多个 Query 头共享一组 Key、Value，缓存更小；
- **GQA（Grouped-Query Attention）**：若干 Query 头共享一组 Key、Value，在质量和效率之间折中。

MQA 或 GQA 能减少 KV 头数，从而降低缓存和内存带宽压力，但具体效果取决于模型训练和实现。

### 5.4 低精度缓存

系统可以用更低精度保存 KV Cache，以降低显存和传输成本。但量化误差会逐层、逐 token 影响注意力结果，长上下文和精确复制任务可能更敏感。

是否使用低精度缓存必须通过目标模型和真实任务评估，不能只看节省比例。

## 6. KV Cache 与位置编码

### 6.1 位置不能错位

模型不仅要知道 token 内容，还要知道它在序列中的位置。复用缓存时，新 token 的位置必须接在已缓存序列之后。

位置偏移错误会让模型把同一份 Key、Value 当成来自错误位置，导致重复、遗漏、逻辑混乱或质量突然下降。

### 6.2 RoPE 的影响

许多模型使用旋转位置编码（RoPE）。实现可能在写入缓存前对 Key 应用位置变换，也可能在读取时处理，具体取决于框架。

缓存的表示方式必须与模型实现一致，不能把一个模型或一种位置策略的缓存直接交给另一个模型使用。

### 6.3 滑动窗口

部分模型只保留最近一段上下文参与某些注意力层。滑动窗口可限制缓存增长，但会丢弃窗口之外的细节。

如果产品需要长期记忆，应通过摘要、检索、外部状态等方式管理，而不是假设无限延长 KV Cache 就能保持可靠记忆。

## 7. 服务系统如何管理缓存

### 7.1 连续批处理

不同用户请求到达和结束的时间不同。连续批处理会在每个解码步动态加入新请求、移除完成请求，提高硬件利用率。

系统必须为每个请求维护正确的缓存位置、长度和遮罩。调度错误可能把不同用户的状态混在一起，属于严重的正确性与隐私问题。

### 7.2 Paged Attention

传统方案常为每个请求预留连续缓存空间，容易产生浪费和碎片。分页式管理把 KV Cache 划分为固定大小的块，通过映射表组织逻辑序列。

它类似操作系统的分页思想：逻辑上连续的 token，不必存放在物理上连续的显存区域。这样更容易分配、回收和共享缓存块。

### 7.3 请求结束后的回收

请求完成、取消或超时后，相关缓存应及时释放。若回收不及时，会出现显存泄漏、并发量下降和服务不稳定。

缓存块重新分配前还要确保旧内容不可被其他请求错误读取。

### 7.4 换出与分层存储

显存不足时，系统可以把部分缓存换到 CPU 内存或其他层级。这样可能保留更多会话，但数据搬运会增加延迟。

是否换出应结合请求优先级、预计恢复时间、网络与总线带宽判断。

## 8. KV Cache 与前缀缓存的区别

### 8.1 单请求 KV Cache

普通 KV Cache 主要在同一个生成请求内部复用历史计算。请求结束后，缓存通常释放。

### 8.2 跨请求前缀缓存

如果多个请求拥有完全相同的长前缀，例如相同系统提示、工具说明或公共文档，服务可以复用此前计算好的前缀缓存块。

这称为 Prefix Caching（前缀缓存）。它可能降低重复 Prefill 成本，但必须正确匹配模型版本、权重、token 序列、位置和相关推理配置。

### 8.3 为什么相似文本不能直接复用

缓存复用要求 token 级前缀一致。两段话即使语义相似，只要 token 不同，Key、Value 就不同。

系统也不能忽略权限边界共享含有私有数据的前缀。命中率优化不能凌驾于租户隔离和数据安全之上。

## 9. 实际例子：长系统提示的客服助手

一家电商为客服助手提供 3,000 token 的系统规则和工具说明，用户问题平均只有 100 token，回答约 200 token。

### 9.1 没有缓存

若每生成一个回答 token 都重新处理系统规则、工具说明、用户问题和已有回答，绝大多数计算都花在重复内容上。

### 9.2 使用请求内 KV Cache

系统先在 Prefill 阶段处理 3,100 token，并保存各层 Key、Value。之后生成 200 个 token 时，每一步只追加新位置的缓存。

这会明显减少重复投影计算，但每一步仍需访问已有上下文，因此长前缀仍会占用显存并影响解码速度。

### 9.3 加入前缀缓存

如果所有客服请求共享完全相同的系统规则和工具定义，可以缓存公共前缀。新请求只需处理用户专属部分。

但以下变化通常会导致前缀无法复用或必须失效：

- 系统提示更新；
- 工具定义或顺序变化；
- 模型或 tokenizer 变化；
- 权限范围变化；
- 在公共前缀中混入用户隐私数据。

### 9.4 应监控什么

团队应至少记录：

1. Prefill 延迟与 Decode 延迟；
2. 首 token 时间与生成速度；
3. 每个请求的缓存字节数；
4. 缓存块利用率和碎片率；
5. 前缀缓存命中率；
6. 因缓存不足导致的排队、换出或拒绝；
7. 不同上下文长度下的回答质量；
8. 请求取消后的缓存回收是否及时。

## 10. 常见优化方向

### 10.1 缩短无效上下文

删除重复提示、无关历史和低价值检索片段，通常能同时减少 Prefill 计算、KV Cache、注意力读取和成本。

上下文压缩必须保留关键约束和证据；简单截断可能让结果更快但更不可靠。

### 10.2 使用 GQA 或适配架构

在模型选择阶段，可比较 MHA、GQA、MQA 对质量、缓存大小和吞吐的影响。架构变化通常需要模型在训练时支持，不能在部署时随意切换。

### 10.3 缓存量化

对 KV Cache 使用较低精度可以提高并发容量，但要按任务测试质量回退，尤其关注长上下文推理、代码、数字和精确检索。

### 10.4 分页与调度

分页缓存、连续批处理和合理的请求调度可以减少碎片，提高显存利用率。系统还可以按上下文长度或服务等级分组，避免单个超长请求拖慢所有用户。

### 10.5 限制与降级

生产系统应设置最大上下文、最大输出、超时和并发配额。资源紧张时可以缩短低优先级上下文、改用小模型、降低并发或明确拒绝，而不是无界占用缓存。

## 11. 局限、风险与常见失败模式

### 11.1 把缓存当成免费加速

KV Cache 省计算但耗显存，还增加内存读取。长上下文下，Decode 可能主要受显存带宽限制。

### 11.2 只按模型权重估算容量

权重能装下不代表服务能承受目标并发。容量规划必须加入每个请求的最大缓存、框架开销和安全余量。

### 11.3 位置或遮罩错误

批处理、填充、滑动窗口和缓存复用中的位置错位，会直接破坏生成结果，而且不一定立刻报错。

### 11.4 缓存跨用户泄漏

错误的块映射、回收或租户隔离可能让一个请求读取另一个请求的历史状态。这是高风险数据泄漏，必须通过内存清理、边界检查和隔离测试防范。

### 11.5 前缀失效规则不完整

模型、提示或工具定义变化后仍使用旧缓存，会让实际上下文与预期不一致。缓存键必须覆盖所有会影响中间表示的因素。

### 11.6 低精度导致质量下降

缓存量化可能在普通问答上影响不明显，却在长距离引用、代码补全或精确数字任务中退化。平均指标会掩盖这些问题。

### 11.7 缓存碎片与回收延迟

大量不同长度的请求会造成空间碎片。取消请求、异常连接或超时处理不完整，还可能形成隐性显存泄漏。

### 11.8 误以为缓存等于长期记忆

KV Cache 只保存当前上下文的中间表示。请求结束或缓存被回收后，它不会自动形成可检索、可治理的长期记忆。

## 12. 如何评估 KV Cache 方案

### 12.1 性能指标

- 首 token 延迟；
- 每秒生成 token 数；
- Prefill 和 Decode 分阶段耗时；
- 不同上下文长度下的吞吐；
- 缓存分配、读取、换出与回收开销。

### 12.2 资源指标

- 单请求 KV Cache 大小；
- 峰值与平均显存；
- 缓存块利用率和碎片率；
- 可维持的并发请求数；
- CPU 与设备间传输量。

### 12.3 质量指标

- 长距离信息引用准确率；
- 代码与数字复制准确率；
- 缓存量化前后的任务差异；
- 不同批次和调度策略下结果是否一致；
- 滑动窗口或截断后的关键信息保留率。

### 12.4 安全与正确性测试

应覆盖缓存块错配、请求取消、超时、模型热更新、前缀失效、跨租户复用和异常重试。高并发压力测试不仅要看速度，也要检查是否发生状态串线。

## 13. KV Cache 与其他方法的关系

### 13.1 与模型量化

模型权重量化减少权重占用；KV Cache 量化减少运行时上下文占用。两者优化对象不同，可以组合使用，也需要分别评估质量。

### 13.2 与 RAG

RAG 把检索资料加入上下文，会增加 Prefill 和 KV Cache。更精确的检索、片段去重和上下文压缩既能改善证据质量，也能降低缓存成本。

### 13.3 与长上下文模型

更大的上下文窗口提供容量上限，不代表使用长上下文没有代价。KV Cache、注意力读取、首 token 延迟和检索噪声仍会随长度增长。

### 13.4 与蒸馏

小模型通常层数、头数或头维度更小，单 token 的 KV Cache 也可能更少。蒸馏可以帮助迁移能力，但不会单独解决错误的缓存管理和服务调度。

## 14. 关键结论

1. KV Cache 保存历史 token 在各注意力层的 Key 和 Value，避免逐 token 生成时重复计算。
2. 推理可分为一次处理输入的 Prefill 和复用缓存的 Decode 两个阶段。
3. 缓存降低重复投影计算，但新 Query 仍需读取历史，因此长上下文解码不会变成常数成本。
4. KV Cache 通常随层数、KV 头数、头维度、序列长度、精度和并发量增长。
5. GQA、MQA、缓存量化、分页管理和连续批处理可改善效率，但各自有质量或工程权衡。
6. 前缀缓存可以跨请求复用完全一致的公共前缀，必须严格处理版本、位置、权限和失效规则。
7. 容量规划要同时考虑模型权重与运行时缓存，不能只看参数量。
8. 缓存错配可能造成质量故障甚至跨用户数据泄漏，正确性和隔离测试不可省略。
9. KV Cache 是推理优化，不是长期记忆机制。

## 15. 延伸思考

- 在固定显存下，应该优先支持更长上下文，还是更多并发请求？
- 如何根据请求长度、优先级和预计输出动态分配缓存？
- 前缀缓存命中率提高后，性能瓶颈会转移到解码、带宽还是调度？
- 缓存量化应如何建立分任务质量门槛，而不是只看平均分？
- 当模型支持滑动窗口时，产品该如何向用户解释“上下文仍在，但部分细节已不可见”？
