# 向量数据库：如何为语义检索组织 Embedding

> 日期：2026-09-17  
> 主题：向量检索、索引结构与 RAG 数据基础设施

## 1. 为什么需要向量数据库

传统数据库擅长按精确条件查找数据，例如：

- 用户 ID 等于 1001；
- 创建日期晚于某一天；
- 商品类别等于“耳机”；
- 标题中包含某个关键词。

但语义检索面对的问题不同。用户可能搜索“续航时间长的降噪耳机”，资料中写的却是“单次使用 40 小时，支持主动降噪”。两段文字没有完全相同的词，却表达了相近含义。

Embedding 模型可以把文本、图片或其他对象编码成向量。语义相近的对象通常在向量空间中距离更近。向量数据库负责高效管理这些向量，并从大量候选中找到最相似的对象。

它通常承担以下工作：

1. 存储向量及其原始内容引用；
2. 建立近似最近邻索引；
3. 执行相似度搜索；
4. 根据元数据进行过滤；
5. 支持新增、更新、删除和权限隔离；
6. 提供延迟、召回率和资源使用方面的工程能力。

向量数据库不是 Embedding 模型本身，也不是完整的 RAG 系统。它是连接“语义表示”与“可检索知识”的基础设施。

## 2. 一条向量记录包含什么

### 2.1 向量

向量通常是一组浮点数：

[
mathbf{x} = [x_1, x_2, ldots, x_d]
]

其中 (d) 是维度。维度由 Embedding 模型决定。不同模型可能产生不同维度、数值分布和语义空间，不能因为维度相同就认为向量可直接混用。

### 2.2 标识符

每条记录需要稳定且唯一的 ID。ID 用于：

- 更新或删除记录；
- 去重；
- 回溯原始文档；
- 关联权限和版本；
- 记录检索日志。

### 2.3 元数据

元数据是结构化字段，例如：

- 文档来源；
- 作者；
-发布时间；
- 部门；
- 租户 ID；
- 语言；
- 文档版本；
- 权限标签；
- 内容类型。

元数据可以帮助系统在向量相似度之外施加业务条件。

### 2.4 原文或引用

系统可以存储文本片段，也可以只保存指向对象存储、关系数据库或文档系统的引用。选择哪种方式取决于内容大小、更新流程、权限模型和数据一致性要求。

一条简化记录可能如下：

```json
{
  "id": "policy-2026-001#chunk-07",
  "vector": [0.012, -0.084, 0.031],
  "text": "企业客户可在合同约定范围内申请退款……",
  "metadata": {
    "tenant_id": "company-a",
    "document_id": "policy-2026-001",
    "version": 3,
    "language": "zh-CN",
    "access_level": "internal"
  }
}
```

## 3. 相似度如何计算

### 3.1 余弦相似度

余弦相似度关注两个向量方向是否接近：

[
cos(mathbf{x}, mathbf{y}) =
rac{mathbf{x} cdot mathbf{y}}
{|mathbf{x}| |mathbf{y}|}
]

取值通常在 -1 到 1 之间。越接近 1，方向越相似。对于经过归一化的向量，余弦相似度与点积排序可以等价。

### 3.2 点积

点积为：

[
mathbf{x} cdot mathbf{y} = sum_i x_i y_i
]

它同时受方向和向量长度影响。有些 Embedding 模型在训练时就针对点积相似度优化。

### 3.3 欧氏距离

欧氏距离衡量两个点的直线距离：

[
d(mathbf{x}, mathbf{y}) =
sqrt{sum_i (x_i-y_i)^2}
]

距离越小通常表示越相似。

### 3.4 距离函数必须与模型匹配

不能只凭习惯选择距离函数。应查看 Embedding 模型的使用说明，并确认向量是否需要归一化。错误的距离函数可能让索引正常运行，却悄悄降低检索质量。

不同系统对“分数”的定义也可能相反：有些返回相似度，数值越大越好；有些返回距离，数值越小越好。接入时必须明确语义。

## 4. 精确搜索与近似最近邻搜索

### 4.1 精确搜索

精确搜索会把查询向量与集合中的全部向量进行比较，再返回最相近的 (k) 条记录。

它的优点是结果准确、逻辑简单，适合：

- 数据量较小；
- 离线评估；
- 为近似索引建立真实基线；
- 对召回率要求极高且延迟可接受的场景。

缺点是计算量通常随数据规模线性增长。数据达到百万、千万甚至更大规模后，逐条比较会变得昂贵。

### 4.2 近似最近邻搜索

近似最近邻搜索（Approximate Nearest Neighbor，ANN）用索引减少需要比较的候选数量，以一定的召回损失换取更低延迟和更高吞吐。

ANN 的目标不是保证每次都找到数学上绝对最近的向量，而是在资源约束内尽量找回真正相关的候选。

工程上常见的权衡包括：

- 召回率与查询延迟；
- 索引大小与内存占用；
- 构建时间与查询速度；
- 更新能力与检索性能；
- 精度与压缩比例。

## 5. 常见索引结构

### 5.1 Flat：直接比较全部向量

Flat 索引本质上接近暴力搜索。它通常提供最可靠的近邻结果，但规模扩大后延迟和计算成本上升。

Flat 常用于：

- 小型知识库；
- 离线基准；
- 检查 ANN 是否丢失重要结果；
- 更新频繁但数据量有限的场景。

### 5.2 IVF：先找分区，再搜候选

倒排文件索引（Inverted File Index，IVF）会先把向量空间划分为多个聚类或分区。查询时先找到最相关的若干分区，再在其中搜索。

关键思想是：不必检查所有数据，只检查可能包含近邻的区域。

需要权衡的参数包括：

- 分区数量；
- 查询时探测多少分区；
- 数据分布是否均衡；
- 新数据是否让原有聚类失效。

探测分区越多，召回率通常越高，但查询成本也会上升。

### 5.3 HNSW：在多层图中寻找近邻

HNSW（Hierarchical Navigable Small World）把向量组织成多层近邻图：

- 上层节点较少，用于快速跳转到大致区域；
- 下层节点更多，用于精细搜索；
- 查询从高层开始，逐层接近目标邻域。

HNSW 常能提供较好的延迟和召回率，但代价可能包括较高内存占用、索引构建成本，以及删除和大规模更新带来的维护复杂度。

常见调节方向包括：

- 建图时每个节点连接的邻居数量；
- 建图时搜索候选范围；
- 查询时探索候选范围。

探索范围越大，召回率一般越高，但延迟也会增加。

### 5.4 PQ：压缩向量以节省存储

乘积量化（Product Quantization，PQ）把高维向量拆成多个子空间，并用码本中的离散编码近似表示每个子向量。

它可以显著降低存储和内存成本，但压缩会引入误差。PQ 常与 IVF 等结构组合使用，在超大规模检索中平衡成本与精度。

不应只看压缩比例，还应评估压缩后关键查询的召回损失。

## 6. Top-k 不等于“找到所有相关内容”

向量检索通常返回相似度最高的 (k) 条记录。这里的 (k) 只是结果数量上限，不是相关性保证。

常见问题包括：

- 前几条内容高度重复；
- 真正关键的证据排在 (k) 之外；
- 相似内容与问题语义接近，却不能回答问题；
- 长文切块后，返回的是背景段落而不是结论段落；
- 查询包含多个子问题，结果只覆盖其中一个。

因此，Top-k 需要结合以下方法：

- 混合检索；
- 查询改写；
- 多路召回；
- 去重与多样性控制；
- 重排序；
- 上下文组装；
- 基于问题的检索评估。

## 7. 元数据过滤的作用

### 7.1 过滤不仅是体验功能

元数据过滤常用于：

- 只检索当前租户的数据；
- 限制为用户有权限访问的文档；
- 只返回某种语言；
- 只搜索有效版本；
- 排除过期内容；
- 限定时间范围或产品类别。

在企业系统中，权限过滤是安全边界的一部分，不能等模型生成答案后再处理。

### 7.2 先过滤还是后过滤

两种常见方式是：

- **预过滤**：先按元数据缩小数据集合，再做向量搜索；
- **后过滤**：先搜索近邻，再从结果中剔除不符合条件的记录。

预过滤更容易保证结果都符合条件，但过滤后集合过小时可能影响索引效率。后过滤实现简单，却可能出现搜索出的前 (k) 条大多被删除，最终返回不足或漏掉合格结果。

不同向量数据库对过滤与 ANN 索引的结合方式不同，需要用真实数据测试，而不能只看接口是否支持过滤。

### 7.3 权限字段要不可伪造

租户 ID、用户组和文档权限应由可信服务端写入并校验。不能接受模型或终端用户自由生成权限过滤条件，否则可能造成跨租户数据泄漏。

## 8. 数据写入流程

### 8.1 文档解析

从 PDF、网页、数据库或知识管理系统中提取正文，同时保留标题、章节、表格位置、来源和版本信息。

### 8.2 切块

把文档拆成适合检索和模型上下文的片段。切块过小会丢失上下文，过大会混入无关内容并增加 Token 成本。

常见策略包括：

- 固定长度切块；
- 按标题和段落切块；
- 带重叠窗口切块；
- 按语义边界切块；
- 为表格、代码和问答对设计专用切块方式。

### 8.3 生成 Embedding

对每个片段调用指定模型生成向量。应记录：

- 模型名称与版本；
- 向量维度；
- 归一化方式；
- 输入预处理规则；
- 生成时间；
- 内容哈希。

### 8.4 写入与建立索引

将 ID、向量、文本或引用、元数据写入系统。大批量导入时通常需要控制批次、失败重试和幂等性，并观察索引何时对查询可见。

### 8.5 质量检查

写入后至少检查：

- 记录数量是否匹配；
- 是否存在空文本或零向量；
- ID 是否重复；
- 元数据是否完整；
- 抽样查询能否找回来源片段；
- 权限过滤是否生效；
- 删除和更新能否正确传播。

## 9. 更新、删除与版本管理

### 9.1 为什么不能只追加

如果知识库只新增、不删除，旧政策、旧价格和失效文档仍可能被检索出来。模型无法可靠判断哪一条才是当前版本。

### 9.2 稳定 ID 与内容哈希

可以用稳定文档 ID 表示逻辑对象，用版本号或内容哈希识别具体内容。这样能够判断：

- 内容是否真的变化；
- 哪些片段需要重新生成向量；
- 哪些旧片段应该删除；
- 是否发生重复导入。

### 9.3 删除需要端到端验证

删除源文档不代表向量索引中的片段自动消失。还应处理：

- 向量记录；
- 文本缓存；
- 重排序缓存；
- 查询结果缓存；
- 备份与审计记录；
- 下游生成上下文。

对隐私删除或合规请求，应有可验证的删除流程和明确的数据保留政策。

### 9.4 更换 Embedding 模型

不同模型的向量通常不在同一语义空间中。更换模型时，常见做法是：

1. 新建独立索引或集合；
2. 用新模型重新编码全部内容；
3. 双写或回放增量变更；
4. 对比新旧索引质量；
5. 灰度切换查询流量；
6. 确认稳定后再下线旧索引。

不要把两个模型生成的向量直接混入同一个索引后继续按同一距离度量搜索。

## 10. 混合检索与重排序

### 10.1 为什么要结合关键词检索

向量检索擅长语义相似，但可能不擅长：

- 精确编号；
- 产品型号；
- 人名和缩写；
- 错别字；
- 代码符号；
- 很少见的新词。

关键词检索对精确词项更敏感。混合检索把稀疏检索与稠密向量检索结合，可以覆盖更多查询类型。

### 10.2 结果融合

不同检索器的分数尺度可能完全不同，不能简单相加。常见做法包括：

- 分数归一化；
- 加权融合；
- 基于排名的融合；
- 分查询类型选择召回器；
- 学习一个融合模型。

### 10.3 重排序

第一阶段检索追求高召回并快速获取候选；第二阶段可使用交叉编码器、重排序模型或业务规则，对候选进行更精细判断。

向量相似度只比较独立编码后的表示。重排序模型可以同时查看查询和候选文本，通常能更准确地判断“这段内容能否回答这个问题”，但计算成本更高。

## 11. 实际例子：构建企业售后政策检索

假设公司有 10 万份售后政策和操作手册，需要让客服助手回答：

> 企业版设备在购买 45 天后出现硬件故障，是否可以直接退款？

### 11.1 数据准备

每份文档按标题和条款切块，并记录：

- 产品线；
- 客户类型；
- 生效日期；
- 失效日期；
- 地区；
- 文档版本；
- 权限级别；
- 原文链接。

### 11.2 查询处理

系统可以先识别查询中的关键条件：

- 客户类型：企业；
- 时间：购买后 45 天；
- 问题类型：硬件故障；
- 诉求：退款。

随后生成查询向量，并使用元数据过滤排除：

- 非企业版政策；
- 已失效版本；
- 用户无权访问的内部文档；
- 不适用地区的条款。

### 11.3 多路召回

向量检索召回“硬件故障处理”“企业客户退款”等语义相关片段；关键词检索补充命中“45 天”“直接退款”和具体产品型号的条款。

系统合并结果、去重并重排序，再把最相关的条款及来源交给大模型。

### 11.4 生成与校验

模型应基于条款回答，并明确：

- 是否满足退款条件；
- 需要先维修还是可以直接退款；
- 时间限制；
- 所需凭证；
- 引用的政策版本和链接；
- 无法确定时需要转人工的原因。

金额、天数和政策状态可以由程序再次校验。这样，向量数据库负责候选召回，模型负责组织语言，但最终可信性来自检索、权限、版本和校验的共同作用。

## 12. 如何评估向量检索

### 12.1 建立带标注的查询集

评测集至少包含：

- 真实用户问题；
- 对应的相关文档或片段；
- 无答案问题；
- 多答案问题；
- 精确编号查询；
- 语义改写；
- 拼写错误；
- 权限受限查询；
- 新旧版本冲突场景。

### 12.2 常见离线指标

- **Recall@k**：相关结果是否出现在前 (k) 条中；
- **Precision@k**：前 (k) 条中有多少是真正相关的；
- **MRR**：第一个相关结果的排名是否靠前；
- **nDCG**：综合考虑相关性等级与排序位置；
- **过滤正确率**：结果是否都满足业务和权限条件；
- **延迟分位数**：不仅看平均延迟，还看 P95、P99。

### 12.3 端到端指标

检索指标高不等于最终回答好。RAG 系统还应评估：

- 答案是否被证据支持；
- 引用是否指向正确片段；
- 关键条件是否完整；
- 无答案时是否正确拒答；
- 是否泄露无权限内容；
- 生成成本与响应时间；
- 用户纠错率和人工接管率。

### 12.4 用精确搜索建立基线

可以在较小样本上用精确搜索作为近似真值，再比较 ANN 索引在不同参数下的 Recall@k 和延迟。这比只观察“看起来搜得还不错”更可靠。

## 13. 选型与容量规划

### 13.1 先描述工作负载

选型前应明确：

- 向量总量和增长速度；
- 向量维度与数据类型；
- 查询 QPS；
- 延迟目标；
- 写入和更新频率；
- 元数据过滤复杂度；
- 多租户和权限要求；
- 备份、容灾与合规要求；
- 是否需要混合检索；
- 团队运维能力。

### 13.2 独立向量数据库不是唯一选择

可选方案包括：

- 在现有关系数据库中使用向量扩展；
- 使用搜索引擎的向量能力；
- 使用独立向量数据库；
- 使用云厂商托管向量检索服务；
- 在单机库或内存索引中完成小规模搜索。

如果数据量不大，且元数据事务和现有数据库集成更重要，未必需要引入新的分布式系统。

### 13.3 容量不能只计算向量本身

除了原始向量，还要考虑：

- 图或倒排索引结构；
- 元数据；
- 文本副本；
- 分片和副本；
- 写入缓冲；
- 删除标记；
- 缓存；
- 备份；
- 索引构建时的临时空间。

同样数量的向量，使用不同索引、精度和副本策略，资源消耗可能差异很大。

## 14. 局限、风险与常见失败模式

### 14.1 语义相似不等于答案相关

一段文字可能与查询主题相近，却没有提供回答所需的具体证据。仅凭相似度分数无法保证可回答性。

### 14.2 切块破坏信息

定义与例外条款可能被分到不同片段，表格行列关系也可能丢失。错误切块会在生成向量前就损坏信息。

### 14.3 索引召回损失

ANN 为速度牺牲部分精确性。参数过于保守时，关键证据可能根本没有进入候选集合。

### 14.4 元数据不完整或过期

即使向量正确，错误的版本号、权限、地区或有效期也会让系统返回不应使用的内容。

### 14.5 跨租户数据泄漏

如果租户过滤依赖不可信输入、过滤发生在错误阶段，或缓存键没有包含租户信息，语义检索可能把其他客户的相似内容返回给当前用户。

### 14.6 Embedding 模型漂移

模型更新后，新旧向量空间不兼容或分布变化，会导致检索质量下降。必须进行版本隔离和重新索引。

### 14.7 只看演示查询

人工挑选的几个问题通常过于简单。真实查询包含短句、歧义、拼写错误、多个条件和无答案场景，需要持续收集失败案例。

### 14.8 把向量数据库当成事实数据库

向量检索是近似的排序过程，不适合替代精确余额、库存、交易状态等强一致数据查询。此类事实应从权威业务系统读取。

## 15. 一个可执行的建设流程

1. 明确检索任务、权限边界和业务风险；
2. 收集真实查询并标注相关文档；
3. 选择 Embedding 模型和匹配的距离函数；
4. 设计文档解析、切块、ID 和元数据规范；
5. 先用小规模精确搜索建立质量基线；
6. 根据规模选择 Flat、HNSW、IVF 或压缩方案；
7. 加入关键词检索、过滤、去重和重排序；
8. 对 Recall@k、延迟、成本和权限正确性进行联合评测；
9. 建立幂等写入、版本切换和可验证删除流程；
10. 上线后记录查询、候选、最终引用和用户反馈；
11. 对模型、索引参数或数据管道变更执行回归测试；
12. 定期清理失效内容并重新评估容量。

## 16. 与其他 AI 技术的关系

### 16.1 与 Embedding 的关系

Embedding 决定语义空间的表示能力，向量数据库负责在这个空间中组织和搜索数据。索引再快，也无法弥补不适合任务的 Embedding。

### 16.2 与 RAG 的关系

向量数据库常是 RAG 的召回组件之一。完整 RAG 还包括数据处理、查询理解、混合检索、重排序、上下文组装、生成、引用和评估。

### 16.3 与重排序的关系

向量检索适合快速缩小候选集合，重排序负责更精细地比较查询与候选。二者通常是召回与精排的分工，而不是互相替代。

### 16.4 与 AI Agent 的关系

Agent 可以调用检索工具获取资料，但工具必须在服务端执行权限过滤并返回可追溯来源。不能让模型自己决定是否遵守权限。

### 16.5 与 AI 记忆的关系

长期记忆可能使用向量检索查找相关历史，但还需要时间、身份、置信度、冲突和遗忘机制。相似度高不代表记忆仍然有效。

## 17. 关键结论

1. 向量数据库负责存储、索引和检索 Embedding，是语义检索与 RAG 的基础组件。
2. 余弦相似度、点积和欧氏距离有不同含义，选择必须与 Embedding 模型匹配。
3. 精确搜索质量可靠但扩展成本高，ANN 通过 Flat、IVF、HNSW、PQ 等方案平衡召回、延迟和资源。
4. Top-k 只是候选数量，不代表结果一定相关；混合检索、重排序和去重通常同样重要。
5. 元数据过滤承担版本、范围和权限控制，必须在可信服务端正确执行。
6. 数据解析、切块、版本和删除流程会直接决定检索质量，不能只优化索引参数。
7. 更换 Embedding 模型通常需要独立索引和重新编码，不能随意混用新旧向量。
8. 评估应同时覆盖 Recall@k、排序、延迟、权限以及最终答案是否被证据支持。
9. 向量检索不能替代强一致业务数据库，也不能单独构成完整安全边界。

## 18. 延伸思考

可以继续思考以下问题：

- 不同内容类型是否应该使用不同的切块和 Embedding 模型？
- 如何让系统根据查询类型动态选择关键词、向量或混合检索？
- 在高过滤比例的多租户场景中，怎样设计索引与分片？
- 如何用用户反馈区分“没有相关文档”和“索引没有召回”？
- 是否能为每条检索结果提供可解释的匹配原因？
- 当知识频繁更新时，怎样在新鲜度、成本和索引稳定性之间权衡？
- 多模态知识库中的文本、图片和音频向量应该如何联合检索？
