# 投机解码：如何让大模型更快生成文本

> 日期：2026-09-10  
> 主题：草稿模型、目标模型、并行验证、接受率、延迟与服务优化

## 1. 什么是投机解码

投机解码（Speculative Decoding）是一类用于加速大语言模型生成的推理方法。

普通自回归解码每次调用大模型只确定一个新 token。投机解码先让一个更快的草稿模型连续提出多个候选 token，再由目标模型用一次并行计算检查这些候选，尽可能一次接受多个 token。

可以概括为：

~~~text
草稿模型快速提出一段候选
          ↓
目标模型并行计算候选位置
          ↓
接受可信前缀，遇到不一致时修正
          ↓
继续下一轮
~~~

它的目标不是让小模型替代大模型，而是用便宜的预测减少目标模型必须逐 token 串行运行的次数。

## 2. 为什么逐 Token 生成会慢

### 2.1 自回归依赖

生成第 10 个 token 前，模型必须先知道前 9 个 token。这个依赖使解码难以像输入预填充那样一次并行处理整段文本。

即使 GPU 很强，每一步也只能推进一个位置，单个请求需要经历许多串行轮次。

### 2.2 Decode 与 Prefill 的差异

推理通常分为：

- **Prefill**：并行处理已有输入，建立 KV Cache；
- **Decode**：反复读取缓存，每步生成一个 token。

Prefill 通常拥有较大的矩阵计算；Decode 每步新增工作很少，却要读取大量模型权重和缓存，容易受显存带宽、调度和通信延迟限制。

### 2.3 单步计算没有充分利用并行能力

目标模型一次只处理一个新位置时，硬件可能无法充分发挥并行吞吐。

如果能把多个待验证位置组成一批，目标模型可以一次计算这些位置的概率分布。这正是投机解码的机会。

## 3. 两个核心角色

### 3.1 目标模型

目标模型是最终决定输出分布的模型。它通常更大、质量更高，也是用户原本想使用的模型。

任何草稿都必须经过目标模型验证，不能仅因为小模型“看起来合理”就直接输出。

### 3.2 草稿模型

草稿模型负责快速产生候选 token。它可以是：

- 参数更少的独立模型；
- 目标模型的蒸馏版本；
- 共享部分结构的轻量预测头；
- 根据目标模型中间表示生成候选的模块；
- 其他低成本候选生成器。

理想草稿模型既要快，又要与目标模型的预测较一致。只有快但总是猜错，验证收益会被额外开销抵消。

### 3.3 两者必须使用兼容的表示

经典方案通常要求草稿与目标模型在 token 序列上能够对齐。若 tokenizer 或词表不兼容，候选无法直接逐位置验证，需要额外映射或采用不同算法。

即使词表相同，聊天模板、特殊 token 和停止条件也必须一致。

## 4. 基本工作流程

### 4.1 生成候选

假设草稿长度为 4。草稿模型根据当前上下文依次提出：

~~~text
t1, t2, t3, t4
~~~

这一步仍是自回归的，但草稿模型更小，因此通常更快。

### 4.2 目标模型并行验证

目标模型把当前上下文和 4 个候选一起送入一次前向计算，得到每个候选位置的目标概率分布。

这些位置在因果遮罩下可以并行计算：第 3 个候选位置能看到前两个候选，但看不到未来位置。

### 4.3 接受候选前缀

系统从第一个候选开始依次判断是否接受。

如果前 3 个候选通过而第 4 个未通过，那么本轮至少可以一次推进 3 个位置，再根据目标模型的分布处理分歧位置。

### 4.4 继续下一轮

已接受 token 被加入上下文和 KV Cache，草稿模型从新位置继续提出候选，直到遇到停止 token、最大长度或其他终止条件。

## 5. 接受与修正的原理

### 5.1 贪心解码中的验证

在贪心生成中，目标模型每一步选择概率最高的 token。

一种直观验证方式是检查草稿 token 是否等于目标模型在该位置的贪心选择。连续相同的候选可以接受；第一次不同处使用目标模型选择，并丢弃之后依赖错误前缀的草稿 token。

如果实现严格遵循目标模型的贪心规则，输出应与普通目标模型贪心解码一致。

### 5.2 采样解码中的接受概率

带温度或随机采样时，不能只比较两个模型的最高概率 token，否则会改变目标分布。

经典投机采样会根据草稿分布和目标分布计算接受概率。对未接受位置，再从经过修正的目标分布中采样。

在算法假设与实现正确的情况下，这种接受—修正机制可以保留目标模型原本的采样分布，而不是把草稿模型偏好混入最终结果。

### 5.3 为什么只能接受连续前缀

后面的候选依赖前面的候选。一旦某个位置被目标模型否决，后续候选是在错误前缀上生成的，不能直接继续使用。

因此一轮通常接受从开头开始的连续候选，而不是任意挑选几个通过的位置。

### 5.4 额外 Token

有些算法在所有草稿 token 都被接受时，还能从目标模型本轮计算出的后续分布再产生一个 token。

这能让一次目标模型调用推进的平均 token 数超过草稿长度的简单接受数，但具体行为取决于实现。

## 6. 加速效果由什么决定

### 6.1 接受率

接受率表示草稿候选被目标模型接受的比例。

接受率越高，一次目标模型验证通常能推进越多 token；接受率低时，大量草稿计算被浪费。

### 6.2 草稿速度

草稿模型必须明显快于目标模型。若草稿本身很大，产生候选的时间可能接近目标模型逐 token 解码，难以获得收益。

### 6.3 验证成本

目标模型一次验证多个位置并不是免费。候选越长，验证计算、缓存和内存占用也会增加。

收益来自“少做串行轮次”，不是让总计算量必然下降。某些场景总 FLOPs 可能增加，但端到端延迟仍然降低。

### 6.4 草稿长度

草稿太短，减少的目标模型轮次有限；草稿太长，后半段更容易因早期分歧全部作废。

最佳长度与模型一致性、任务类型、采样参数和硬件有关，不能固定套用。

### 6.5 批次与并发

投机解码对单请求延迟可能有帮助，但服务系统还要考虑多用户批处理。

不同请求每轮接受的 token 数不同，序列进度会分叉，增加调度复杂度。高并发下，普通连续批处理已经能充分利用硬件时，投机解码的额外收益可能缩小。

## 7. 哪些内容更容易被接受

### 7.1 可预测文本

固定格式、常见短语、代码样板、标点和重复结构通常更容易让草稿与目标模型一致。

例如 JSON 字段名、Markdown 列表格式或常见函数结构可能拥有较高接受率。

### 7.2 高不确定性内容

创意写作、开放推理、罕见知识、多个合理表达和高温度采样更容易产生分歧。

目标模型与草稿模型能力差距越大，复杂任务中的接受率通常越不稳定。

### 7.3 上下文分布

如果草稿模型没有见过目标场景，例如专业术语、多语言混合或特殊聊天模板，它可能在这些请求上频繁失败。

平均接受率不能代表所有用户，应按语言、任务、输入长度和输出类型切分监控。

## 8. 草稿模型如何选择

### 8.1 使用同系列小模型

同一模型系列的小版本可能共享 tokenizer、训练分布和表达习惯，便于对齐。

但“同系列”不保证高接受率，仍要在真实请求上测试。

### 8.2 使用蒸馏模型

可以让小模型学习目标模型的输出分布，使草稿更接近目标策略。

蒸馏会增加训练和版本维护成本。目标模型更新后，旧草稿的接受率可能下降，需要重新评估。

### 8.3 动态路由

系统可以根据请求特征选择草稿模型或关闭投机解码。例如，固定格式生成使用较长草稿，复杂推理使用较短草稿或普通解码。

路由策略本身也需要成本，错误分类可能让性能更差。

### 8.4 自投机方案

某些方法从目标模型的较浅层、中间表示或额外预测头生成多个候选，减少维护独立草稿模型的负担。

这类方案仍需验证候选，并在额外结构、训练复杂度与速度收益之间权衡。

## 9. 实际例子：代码补全服务

一个代码助手使用大型目标模型生成函数实现，并使用同词表的小模型作为草稿模型。

### 9.1 容易加速的片段

小模型可能准确预测：

- 缩进和括号；
- 常见变量赋值；
- 循环与条件语句模板；
- 重复的类型标注；
- 测试断言的固定结构。

目标模型一次验证多行中的若干 token，连续接受后减少串行轮次。

### 9.2 容易分歧的片段

当代码涉及：

- 新 API；
- 复杂业务规则；
- 罕见库；
- 长距离变量依赖；
- 安全关键判断；

草稿模型可能频繁猜错。目标模型应在第一次分歧处修正，不能因为草稿代码能运行就放弃验证。

### 9.3 应监控的指标

团队应记录：

1. 每轮候选 token 数；
2. 平均连续接受长度；
3. 按语言和仓库类型切分的接受率；
4. 草稿、验证和调度分别耗时；
5. 首 token 延迟与后续生成速度；
6. 单请求和高并发吞吐；
7. 输出是否与基线解码保持预期一致；
8. GPU 利用率、显存和功耗；
9. 不同采样参数下的质量；
10. 停止条件和工具调用格式是否正确。

## 10. 服务系统中的工程要点

### 10.1 双模型显存

独立草稿模型和目标模型都要加载权重。若显存紧张，小模型占用可能挤压目标模型批次或 KV Cache，反而降低总体吞吐。

可以把草稿模型放在不同设备上，但跨设备通信会增加延迟。

### 10.2 KV Cache 协调

草稿模型与目标模型通常各自维护缓存。目标模型只应把最终接受的前缀提交到有效缓存状态。

被拒绝候选对应的临时缓存需要丢弃或回滚，否则后续生成会基于错误历史。

### 10.3 连续批处理

请求接受长度不同，会在一次验证后推进不同距离。调度器必须正确处理动态序列长度、缓存块和完成状态。

### 10.4 停止条件

候选中可能提前出现停止 token、工具调用结束标记或结构化输出边界。系统必须按目标模型验证后的有效序列处理停止，不能根据未接受的草稿提前结束。

### 10.5 版本一致性

目标模型、草稿模型、tokenizer、聊天模板和解码参数都应版本化。

升级任何一项后，都应重新测量接受率、输出一致性和性能，不能假设旧配置仍然有效。

## 11. 如何评估投机解码

### 11.1 延迟指标

- 首 token 延迟；
- token 间延迟；
- 完整回答耗时；
- 每秒输出 token 数；
- P50、P95 和 P99 延迟。

平均速度提升可能掩盖长尾请求变慢。

### 11.2 吞吐指标

- 每秒完成请求数；
- 目标模型每次调用平均推进 token 数；
- 固定显存下的并发容量；
- 高并发时的排队时间；
- 单位任务的计算和能源成本。

### 11.3 一致性与质量

贪心场景可逐 token 对比普通目标模型输出。采样场景应比较整体分布、任务质量和安全指标，而不是要求每次随机结果完全相同。

工具调用、JSON、代码、数学和停止行为需要单独回归。

### 11.4 分场景分析

按以下维度切分：

- 输入和输出长度；
- 语言；
- 代码与自然语言；
- 创意与事实任务；
- 温度和采样策略；
- 草稿长度；
- 并发水平；
- 硬件类型。

只有在目标部署条件下测量，才能判断真实收益。

## 12. 局限、风险与常见失败模式

### 12.1 接受率高但没有加速

如果验证、调度、模型切换和缓存管理开销太大，即使候选经常通过，端到端延迟也可能不降。

### 12.2 只看 Token 每秒

更高的 token 速度不代表用户更快得到有用答案。首 token、完整任务时间和队列延迟同样重要。

### 12.3 草稿模型占用过多资源

额外模型会消耗显存、带宽和运维成本，可能降低高并发服务的总体容量。

### 12.4 错误实现改变输出分布

采样验证若没有正确执行接受与修正，会把草稿模型偏差带进最终输出，导致质量或安全行为变化。

### 12.5 缓存回滚错误

拒绝候选后若缓存状态没有正确恢复，模型会基于未输出 token 继续生成，造成难以发现的错误。

### 12.6 任务分布变化

线上流量从固定格式转向复杂推理、多语言或新领域时，接受率可能突然下降。

### 12.7 高并发收益反转

投机解码对单请求更快，却可能使批处理更不规则。在吞吐优先的场景中，普通批处理有时更合适。

### 12.8 忽略失败回退

草稿模型不可用、超时或版本不兼容时，系统应安全切回普通目标模型解码，不能中断请求或输出未验证内容。

## 13. 一套可落地的实践顺序

1. 建立目标模型普通解码的延迟、吞吐和质量基线；
2. 从兼容 tokenizer 的小模型开始；
3. 统计真实请求中的接受长度分布；
4. 在少量草稿长度上做对照实验；
5. 分离草稿、验证、调度和通信耗时；
6. 检查贪心输出一致性与采样分布正确性；
7. 验证停止 token、工具调用和结构化输出；
8. 同时测试低并发延迟与高并发吞吐；
9. 将双模型权重和双份缓存计入容量规划；
10. 按任务动态决定是否启用投机解码；
11. 为草稿故障设计普通解码回退；
12. 模型或模板升级后重新评估。

## 14. 与其他推理优化的关系

### 14.1 与 KV Cache

KV Cache 避免重复计算历史 token 的 Key 和 Value；投机解码减少目标模型串行调用次数。两者优化不同环节，通常可以组合。

### 14.2 与模型量化

量化降低目标模型或草稿模型的权重与计算成本。草稿模型量化后更快，但精度下降也可能降低接受率，需要看端到端结果。

### 14.3 与知识蒸馏

蒸馏可以训练更贴近目标模型的草稿模型，提高候选质量。维护成本和目标模型版本同步是主要代价。

### 14.4 与连续批处理

连续批处理通过合并多个用户请求提升吞吐；投机解码通过单个请求多 token 验证减少串行轮次。两者组合会增加调度复杂度。

### 14.5 与多 Token 预测

多 Token 预测让模型或附加预测头一次提出多个未来 token，也可以作为候选来源。候选仍需被可靠验证，不能直接假设全部正确。

## 15. 关键结论

1. 投机解码用快速草稿生成多个候选，再由目标模型并行验证。
2. 它减少的是目标模型串行解码轮次，不保证总计算量一定减少。
3. 加速效果由接受率、草稿速度、验证成本、草稿长度、并发和硬件共同决定。
4. 一轮只能安全接受从开头开始的连续候选，分歧后的候选依赖错误前缀。
5. 正确的贪心验证应保持目标模型贪心输出；正确的投机采样可保持目标采样分布。
6. 草稿与目标模型需要兼容的 token 表示、模板、停止条件和版本管理。
7. 独立草稿模型会增加权重、缓存和调度成本，高并发下收益可能与单请求不同。
8. 拒绝候选时必须正确回滚缓存，任何未验证 token 都不能直接输出。
9. 是否启用投机解码应依据真实流量的端到端延迟、吞吐与质量评估。

## 16. 延伸思考

- 接受率、草稿长度和验证批量之间是否可以由系统在线动态调整？
- 当目标模型升级时，怎样快速判断现有草稿模型是否仍然合适？
- 单请求延迟和全局吞吐冲突时，调度器应该优先优化哪一个？
- 能否根据任务难度选择不同草稿模型，而不让路由成本抵消收益？
- 随着目标模型具备更强的多 Token 预测能力，独立草稿模型是否仍有必要？
