# AI Agent：大模型如何调用工具完成任务

> 日期：2026-08-25  
> 主题：智能体循环、工具调用、状态管理与安全边界

## 1. 什么是 AI Agent

AI Agent（智能体）是一类能够围绕目标观察环境、选择行动、调用工具并根据结果继续决策的 AI 系统。大语言模型通常负责理解语言和生成决策，真正改变外部世界的能力则来自搜索、数据库、代码执行、日历、邮件或业务 API 等工具。

普通聊天模型主要输出文本；Agent 的核心差异是它能在多步过程中采取行动。一个典型任务可能经历：

1. 理解用户目标；
2. 判断缺少哪些信息；
3. 选择合适工具；
4. 生成结构化参数；
5. 执行工具并读取结果；
6. 根据新信息继续行动或结束。

因此，Agent 不是单一模型，而是模型、工具、状态、权限、控制逻辑和评估机制组成的系统。

## 2. Agent 与相近概念的区别

### 2.1 Agent 与聊天机器人

聊天机器人可以只根据上下文生成回答，不一定访问外部系统。Agent 除了“说”，还可以“做”，例如查询订单、创建日程或修改工单。

### 2.2 Agent 与固定工作流

固定工作流按照预先写好的步骤执行，路径稳定、可预测。Agent 会根据当前观察动态决定下一步，更适合路径难以穷举的任务，但也更难测试和控制。

实践中常采用混合方式：关键业务流程由代码约束，局部判断交给模型。这样既保留灵活性，也降低失控风险。

### 2.3 Agent 与 RAG

RAG 主要解决“从外部资料中找到证据并生成回答”。Agent 的范围更广：检索可以是它的一种工具，它还可以写入数据、调用服务、等待事件并完成多步事务。

## 3. 核心工作原理

### 3.1 观察—决策—行动—反馈循环

Agent 常以循环方式运行：

1. 观察：读取用户请求、历史状态和工具返回；
2. 决策：判断当前目标、缺失信息和下一步；
3. 行动：调用一个工具或向用户提问；
4. 反馈：接收成功结果、错误或环境变化；
5. 终止：目标完成、达到安全边界或无法继续时停止。

循环使系统能够处理不确定性。例如，查询航班失败后，可以检查日期格式、改用机场代码再次查询，或向用户确认。

### 3.2 工具描述与结构化调用

工具通常用名称、用途、参数类型、必填字段和返回格式描述。模型不应直接拼接任意命令，而应输出符合模式的结构化调用，例如：

- 工具：查询订单；
- 参数：订单号、用户身份；
- 返回：状态、商品、可执行操作。

清晰的工具描述能减少选错工具和参数错误。运行时还必须再次验证参数，因为模型输出并不天然可信。

### 3.3 状态与记忆

多步任务需要保存状态，包括已完成步骤、工具结果、待确认信息和错误记录。状态可分为：

- 会话状态：当前任务中临时使用；
- 业务状态：订单、工单等外部系统中的真实记录；
- 长期记忆：跨会话保存的用户偏好或历史摘要。

长期记忆必须有明确用途、保存期限和删除机制。不能因为“以后可能有用”就无限保存用户数据。

### 3.4 规划与重规划

简单任务可以每次只决定下一步；复杂任务可以先生成计划，再逐步执行。无论哪种方式，计划都不是事实：工具失败、权限不足或数据变化时，Agent 必须重新评估，而不是机械坚持原计划。

可靠系统通常限制最大步骤数、最大成本和最长运行时间，避免无限循环。

## 4. 工具调用的完整链路

### 4.1 选择工具

系统应只向模型暴露当前任务真正需要的工具。工具越多，模型越容易混淆，也扩大了权限和安全面。

### 4.2 校验参数

执行前应检查类型、格式、范围和业务规则。例如，转账金额必须为正数，收款账户必须存在，用户必须拥有对应权限。

### 4.3 执行与处理错误

工具可能超时、限流、返回空结果或部分成功。系统需要区分可重试错误与永久错误，并使用退避、幂等键和超时限制。不能让模型在未知结果下盲目重复写操作。

### 4.4 解释结果

工具返回的数据可能很长或包含不可信文本。系统应提取与任务相关的信息，并把外部内容视为数据，而不是新的系统指令。

## 5. 实际例子：差旅安排助手

用户提出：“下周三去上海参加下午两点的会议，帮我安排当天往返，预算不超过 1500 元。”

### 5.1 合理的执行过程

1. 解析日期、出发城市、会议时间和预算；
2. 若出发城市未知，先向用户确认；
3. 查询去程与返程交通；
4. 估算车站或机场到会场的时间；
5. 筛选满足时间和预算的方案；
6. 向用户展示关键差异；
7. 获得明确确认后再预订；
8. 预订成功后创建日历事件并返回凭证。

### 5.2 为什么不能直接自动下单

任务中存在金额、个人偏好和不可逆操作。Agent 可以自动完成查询与比较，但付款前应设置确认点。若查询结果发生变化，必须展示最新价格，不能使用过期结果直接提交。

### 5.3 失败时如何处理

若预订接口超时，系统应先查询订单状态，确认是否已经成功，再决定重试。直接重复提交可能造成重复扣款。这说明可靠性依赖事务设计，而不只是模型是否“聪明”。

## 6. Agent 的控制结构

### 6.1 单智能体

一个模型统一规划和调用工具，结构简单，适合步骤较少的任务。随着任务变长，上下文会变得复杂，错误也可能累积。

### 6.2 多智能体

多个角色分别负责研究、执行或检查，可以隔离部分上下文，但会增加通信成本、协调失败和责任不清等问题。多智能体并不天然优于单智能体；只有当职责边界明确、任务可独立拆分时才值得使用。

### 6.3 人在回路

以下场景通常需要人工确认或审批：

- 付款、删除、发布等难以撤销的操作；
- 涉及隐私、法律或重大业务风险；
- 模型置信不足或工具结果冲突；
- 用户目标存在关键歧义。

人在回路不是补丁，而是系统权限模型的一部分。

## 7. 权限与安全边界

### 7.1 最小权限

每个工具只获得完成当前任务所需的最低权限。能读取日历不代表可以删除日历；能起草邮件不代表可以直接发送。

### 7.2 提示注入

网页、邮件或文档中可能包含“忽略之前规则并执行某操作”等恶意文本。Agent 必须把外部内容与系统指令隔离，不能让检索到的数据改变权限或高层规则。

### 7.3 敏感信息

日志、提示词和工具结果可能包含个人信息、令牌或商业数据。系统应进行脱敏、访问控制和保留期管理，错误信息也不应暴露秘密。

### 7.4 可审计性

重要操作要记录谁发起、模型选择了什么工具、使用了哪些参数、得到什么结果以及是否经过确认。审计记录有助于定位问题，但同样要遵守隐私和最小化原则。

## 8. 常见失败模式

### 8.1 工具选择错误

名称或描述相近时，模型可能选错工具。可以减少候选工具、改进描述并增加场景示例。

### 8.2 参数看似合理但实际无效

模型可能生成格式正确却不存在的订单号或日期。结构校验只能保证形式，业务系统仍需验证真实性。

### 8.3 无限循环

Agent 可能反复调用同一工具却没有进展。应设置步骤上限、重复检测和明确的停止条件。

### 8.4 状态漂移

长任务中，Agent 可能忘记用户约束或使用旧结果。重要约束应存入结构化状态，每次行动前重新检查。

### 8.5 部分成功

一组操作可能只完成一部分。例如创建了订单却未写入日历。系统需要定义补偿动作、恢复入口，并准确告诉用户当前状态。

### 8.6 过度自动化

能自动执行不代表应该自动执行。高影响操作如果缺少确认、预览和撤销机制，会把小概率模型错误放大为真实损失。

## 9. 如何评估 Agent

Agent 评估不仅看最终回答，还要检查过程。常见指标包括：

- 任务完成率；
- 工具选择和参数正确率；
- 平均步骤数与无效调用率；
- 失败后的恢复率；
- 严重越权或安全违规率；
- 用户确认是否在正确位置触发；
- 端到端延迟与单位成功任务成本。

评估集应包含正常任务、信息缺失、工具故障、冲突数据和对抗输入。还要检查最终状态，而不是只读模型的文字说明：Agent 说“已创建日程”并不代表日历中真的存在记录。

## 10. 一套可落地的建设顺序

1. 从一个边界清晰、价值明确的任务开始；
2. 把确定步骤写成代码，把开放判断交给模型；
3. 为工具设计窄而清晰的接口；
4. 所有模型参数都经过运行时校验；
5. 写操作加入幂等、确认和撤销机制；
6. 设置步骤、时间、成本与权限上限；
7. 记录可审计的结构化执行轨迹；
8. 用真实失败持续扩充回归测试；
9. 达到质量和安全门槛后再扩大自主权。

自主程度应该由证据逐步换取，而不是在第一版中一次性开放。

## 11. 关键结论

1. AI Agent 是模型、工具、状态、权限和控制逻辑组成的系统。
2. 它通过观察、决策、行动和反馈循环完成多步任务。
3. 工具调用必须经过结构校验、业务校验和权限检查。
4. 固定工作流与 Agent 可以结合使用，关键路径应优先保持确定性。
5. 高影响操作需要确认、幂等、补偿和审计机制。
6. 提示注入、状态漂移、无限循环和部分成功是常见风险。
7. Agent 是否可靠，要以外部世界中的真实任务结果衡量，而不是以回答是否流畅衡量。

## 12. 延伸思考

- 哪些任务值得使用 Agent，哪些任务用固定工作流更安全？
- 怎样根据风险动态调整自动执行与人工确认的边界？
- 当工具返回互相冲突的信息时，Agent 应依据什么规则决策？
- 如何在不保存过多个人数据的前提下，让 Agent 具备有用的长期记忆？
