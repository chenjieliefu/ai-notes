# AI 记忆系统：如何让 Agent 跨会话保持上下文

> 日期：2026-09-12  
> 主题：工作记忆、长期记忆、检索、写入策略、冲突处理与隐私治理

## 1. 什么是 AI 记忆系统

AI 记忆系统是让模型在当前上下文之外保存、检索和更新信息的一组机制。

大语言模型本身不会因为完成一次对话就自动永久记住内容。模型权重通常在推理时保持不变；对话结束后，若应用没有把信息保存到外部存储，下一次请求就无法直接使用这些内容。

一个完整的记忆系统通常包含：

1. 从当前交互中识别值得保存的信息；
2. 用结构化形式或向量表示写入存储；
3. 在未来任务中检索相关记忆；
4. 把记忆放回模型上下文；
5. 处理冲突、过期、撤回和删除；
6. 评估记忆是否真正帮助任务。

记忆的目标不是保存一切，而是在合适的时间提供正确、经过授权且仍然有效的信息。

## 2. 记忆与上下文窗口的区别

### 2.1 上下文窗口

上下文窗口是模型单次推理能够读取的 token 范围，包括系统指令、用户消息、工具结果、检索资料和历史对话。

窗口内的信息可以直接影响本次输出，但长度有限，也会增加延迟和成本。

### 2.2 外部记忆

外部记忆存放在数据库、文件、向量索引或专门的状态服务中。它可以跨请求、跨会话保存，但模型无法自动看到，必须由应用检索并注入上下文。

### 2.3 模型权重

预训练和微调把模式写入模型参数，适合稳定、广泛的能力。它们不是保存某个用户近期偏好或某个项目最新状态的理想方式。

可以把三者区分为：

~~~text
模型权重：长期、广泛、更新成本高
外部记忆：可管理、可检索、可更新
上下文窗口：当前推理可直接使用的信息
~~~

## 3. 常见记忆类型

### 3.1 工作记忆

工作记忆保存当前任务正在使用的短期状态，例如：

- 已完成步骤；
- 待办事项；
- 中间计算结果；
- 工具调用返回；
- 当前计划；
- 仍需用户确认的问题。

它通常与一次任务绑定，任务结束后可以压缩、归档或删除。

### 3.2 情景记忆

情景记忆记录过去发生的具体事件，例如“用户上周选择了方案 B”“某次部署因为环境变量缺失而失败”。

它应包含时间、来源和上下文，否则旧事件容易被误当成当前事实。

### 3.3 语义记忆

语义记忆保存相对稳定的事实或知识，例如用户偏好的输出语言、团队术语和项目架构。

这类记忆需要明确适用范围。用户在一个项目中的偏好，不应自动扩展到所有场景。

### 3.4 程序记忆

程序记忆描述完成任务的方法，例如发布流程、检查清单或工具使用规范。

它更像可执行规则或工作流，应版本化并与普通事实分开，因为错误程序可能反复产生副作用。

### 3.5 用户档案与项目状态

用户偏好、身份信息、权限和项目状态常被视为记忆，但它们的治理要求不同。

权限必须查询权威系统，不能只相信模型记忆；项目状态也应以仓库、任务系统或数据库的当前数据为准。

## 4. 记忆的基本生命周期

### 4.1 候选提取

系统从对话、工具结果或用户操作中识别可能值得保存的内容。

并非每句话都应成为记忆。寒暄、临时想法、敏感数据和未经确认的推测通常不适合长期保存。

### 4.2 写入决策

写入前要判断：

- 未来是否可能复用；
- 信息是否足够稳定；
- 来源是否可信；
- 用户是否同意或预期会被保存；
- 是否包含敏感信息；
- 保存多久；
- 适用于哪个用户、项目或组织。

### 4.3 存储

记忆可以保存为结构化记录、全文、摘要、向量或多种形式的组合。

结构化记录便于更新和精确过滤；全文保留细节；摘要降低上下文成本；向量便于语义检索。

### 4.4 检索

新任务到来时，系统根据用户、项目、权限、时间和语义相关性查找候选记忆。

### 4.5 使用

检索结果被放入模型上下文，并清楚标记来源、时间和可信度。模型使用记忆形成回答或计划。

### 4.6 更新与遗忘

当用户改变偏好、事实过期或项目状态变化时，系统应更新、失效或删除旧记忆，而不是无限追加互相冲突的记录。

## 5. 什么信息值得保存

### 5.1 高价值特征

适合保存的信息通常具有：

- 未来重复使用价值；
- 较长有效期；
- 清晰来源；
- 明确适用范围；
- 可验证或由用户确认；
- 保存收益大于隐私和维护成本。

例如“这个项目统一使用 Python 3.12”比“今天有点累”更适合成为项目记忆。

### 5.2 用户明确要求记住

当用户明确说“记住以后都用中文回答”时，写入意图最清楚。

系统仍应允许用户查看、修改和删除，并避免把局部要求错误扩大到其他上下文。

### 5.3 从行为中推断偏好

根据多次行为推断偏好更有风险。例如用户连续两次选择简短回答，不代表永远不需要详细解释。

推断记忆应标记为推测、设置较短有效期，或在影响重要结果前向用户确认。

### 5.4 不应默认保存的内容

通常不应默认长期保存：

- 密码和访问令牌；
- 完整身份证件；
- 未经同意的医疗或财务敏感信息；
- 一次性验证码；
- 第三方私密内容；
- 模型自己的未经验证推测；
- 与未来任务无关的原始对话。

## 6. 记忆如何表示

### 6.1 结构化记录

一条记忆可以包含：

~~~json
{
  "subject": "project:ai-notes",
  "fact": "每篇笔记发布后更新 README 目录",
  "source": "user_explicit",
  "created_at": "2026-08-21",
  "valid_from": "2026-08-21",
  "expires_at": null,
  "confidence": "confirmed",
  "scope": "project",
  "status": "active"
}
~~~

结构化元数据支持权限过滤、冲突检测和过期处理。

### 6.2 原文与摘要

原文便于审计，却可能冗长并包含敏感信息；摘要节省空间，但会遗漏细节或引入模型解释。

重要记忆可以同时保存受控原文引用与独立摘要，并记录摘要由谁、何时、基于什么生成。

### 6.3 向量表示

Embedding 可以把记忆映射为向量，支持语义相似搜索。

向量相似只表示内容接近，不代表记忆最新、正确或有权限使用。检索必须结合元数据过滤。

### 6.4 关系和实体

复杂项目可把人物、组织、文件、决策和任务表示为实体及关系。

知识图谱或关系数据库有利于回答“谁决定了什么”“哪个任务依赖哪个版本”，但构建和更新成本更高。

## 7. 记忆检索如何工作

### 7.1 关键词与精确过滤

用户 ID、项目 ID、日期、标签和状态适合精确过滤。

例如检索当前项目记忆时，应先限定 project_id，而不是在所有用户数据中做全局语义搜索。

### 7.2 语义检索

语义检索适合用户换一种说法时找到相关记忆，例如“发布文章后的索引维护”可以匹配“更新 README 目录”。

### 7.3 混合检索

实际系统常组合：

1. 权限和范围过滤；
2. 关键词搜索；
3. 向量相似；
4. 时间衰减；
5. 重要度；
6. 重排序；
7. 去重与冲突处理。

### 7.4 检索数量

取回太少可能漏掉关键背景；太多会增加 token、干扰模型并放大旧信息。

应根据任务动态控制数量，而不是每次把全部历史塞进上下文。

## 8. 时间、冲突与真相来源

### 8.1 记忆会过期

“项目负责人是小王”可能在几个月后失效。每条事实应尽量记录创建时间、有效期和最后验证时间。

### 8.2 新信息不一定自动覆盖旧信息

用户说法可能是更正，也可能只适用于当前场景。系统需要比较来源、时间、范围和权威程度。

### 8.3 权威数据优先

涉及账户权限、付款状态、库存、日历和仓库内容时，应以当前业务系统为准。

记忆可以帮助决定查什么，但不能替代实时查询。

### 8.4 保留变更历史

直接覆盖旧值会丢失审计线索。重要状态可以保留版本：

~~~text
旧值：报告每周一发送
新值：报告每周五发送
变更时间：2026-09-12
来源：用户明确指令
~~~

运行时只使用当前有效版本。

## 9. 记忆压缩与巩固

### 9.1 为什么需要压缩

长期保存每条消息会造成存储膨胀、检索噪声和隐私风险。

系统可以把多条重复事件压缩为更稳定的摘要，例如把多次格式修改归纳为“用户偏好表格先给结论，再给说明”。

### 9.2 巩固过程

一种常见流程是：

1. 聚合同一主题的近期事件；
2. 提取重复模式；
3. 保留来源链接；
4. 生成候选稳定记忆；
5. 检查是否与现有记忆冲突；
6. 设置有效期和范围；
7. 必要时请求用户确认。

### 9.3 摘要漂移

反复对摘要再摘要会逐渐改变含义。系统应保留可追溯来源，并定期从原始证据重新生成，而不是无限递归压缩。

### 9.4 重要度不是固定的

某条记忆对一个任务无关，对另一个任务可能关键。重要度应同时考虑全局价值和当前任务相关性。

## 10. 实际例子：长期项目助手

一个 Agent 持续协助团队维护软件项目，包括需求、代码、发布和故障复盘。

### 10.1 应保存的记忆

可以保存：

- 项目使用的技术栈和版本；
- 用户明确的代码风格；
- 已通过的架构决策；
- 发布流程与审批人；
- 重复出现的故障根因；
- 尚未完成的承诺；
- 关键文件和文档位置。

### 10.2 不应只靠记忆的状态

以下内容应实时查询：

- 当前分支和提交；
- 测试是否通过；
- 线上版本；
- 工单状态；
- 用户权限；
- 密钥有效性；
- 服务健康状态。

### 10.3 一次交互流程

用户说：“把支付模块按上次的灰度流程发布。”

助手应：

1. 检索“支付模块”和“灰度流程”的项目记忆；
2. 显示记忆的来源和更新时间；
3. 查询仓库、测试和部署系统的当前状态；
4. 发现流程版本已更新时，以当前权威文档为准；
5. 生成本次执行计划；
6. 高风险步骤请求具体确认；
7. 完成后把真实结果写入任务记录；
8. 只在有长期价值时更新记忆。

### 10.4 错误做法

如果助手只记得“上次直接发布成功”，就跳过当前测试和审批，这是把历史经验误当成当前授权。

记忆应该减少重复沟通，不能绕过实时验证。

## 11. 记忆的隐私与安全风险

### 11.1 过度收集

保存所有对话看似能提升个性化，却会积累大量不必要敏感数据。

应采用数据最小化：只保存完成未来任务所需的信息。

### 11.2 跨用户泄漏

检索过滤错误可能把一个用户或项目的记忆提供给另一个用户。

访问控制必须在数据库查询层强制执行，不能让模型自行判断“这条记忆是否属于当前用户”。

### 11.3 提示注入持久化

外部网页或文档中的恶意指令可能被误写入长期记忆，未来反复影响 Agent。

自动记忆写入必须把不可信内容视为数据，并限制它成为程序规则或高权限指令。

### 11.4 敏感数据被摘要保留

即使删除原始对话，摘要或向量索引中仍可能保留敏感信息。删除流程应覆盖所有派生数据和备份策略。

### 11.5 用户缺乏控制

用户应能知道系统记住了什么、为什么使用、如何纠正和删除。

不可见且不可撤回的个性化会降低信任，也难以满足合规要求。

## 12. 局限、风险与常见失败模式

### 12.1 记住错误事实

模型从含糊对话中提取了错误结论，之后每次检索都强化这个错误。

### 12.2 记忆作用域过宽

项目内偏好被应用到所有项目，个人选择被当成团队规则。

### 12.3 新旧记忆冲突

系统同时取回“周一发布”和“周五发布”，却没有根据版本和时间判断哪条有效。

### 12.4 只按相似度排序

语义最相似的记忆可能已经过期、没有权限或来源不可信。

### 12.5 把所有历史放入上下文

过量记忆增加成本并分散注意力，重要规则反而更难被模型使用。

### 12.6 自动写入未经确认的推断

模型把一次临时选择固化为永久偏好，让未来交互越来越偏离用户真实意图。

### 12.7 没有遗忘机制

无效信息不断累积，导致检索质量下降、隐私风险扩大和存储成本增长。

### 12.8 记忆替代实时系统

用旧记忆判断权限、余额或部署状态，会产生严重错误。

### 12.9 删除不彻底

只删除展示层记录，却保留摘要、向量或缓存，导致用户以为信息已被遗忘。

## 13. 如何评估记忆系统

### 13.1 检索质量

- 相关记忆召回率；
- 无关记忆比例；
- 最新有效版本命中率；
- 跨用户错误召回率；
- 检索延迟和 token 成本。

### 13.2 写入质量

- 值得保存的信息捕获率；
- 不必要写入比例；
- 未经确认推断写入率；
- 敏感数据误写率；
- 作用域和有效期正确率。

### 13.3 任务效果

比较开启和关闭记忆时：

- 任务完成率；
- 重复提问次数；
- 用户纠正次数；
- 工具调用成功率；
- 严重错误率；
- 端到端时长。

### 13.4 长期一致性

测试用户偏好变化、项目迁移、多人协作和长期不活跃后的行为，检查系统能否正确更新而不是执着于旧信息。

### 13.5 安全评估

应覆盖：

- 跨租户检索；
- 恶意记忆写入；
- 间接提示注入；
- 删除与撤回；
- 权限变更；
- 敏感信息查询；
- 记忆导出和审计。

## 14. 一套可落地的设计顺序

1. 明确记忆要改善的具体任务；
2. 区分工作、情景、语义和程序记忆；
3. 定义哪些信息禁止长期保存；
4. 为每条记忆记录来源、时间、范围和状态；
5. 对用户明确指令与模型推断采用不同信任级别；
6. 先做权限和作用域过滤，再做语义检索；
7. 结合关键词、向量、时间和重要度重排序；
8. 控制注入上下文的记忆数量；
9. 用权威系统校验实时状态；
10. 为冲突、过期和撤回设计明确规则；
11. 提供查看、更正、导出和删除入口；
12. 对摘要和向量等派生数据执行完整删除；
13. 建立记忆污染和跨用户泄漏测试；
14. 用真实任务评估，而不是只看检索相似度。

## 15. 与其他 AI 方法的关系

### 15.1 与 RAG

RAG 通常从外部知识库检索事实；记忆系统更关注用户、项目和历史交互状态。两者都需要索引、检索、权限和来源管理。

### 15.2 与 Embedding

Embedding 支持语义检索，但不能判断事实是否有效。元数据过滤、时间和权威来源仍然必要。

### 15.3 与上下文工程

记忆检索结果只是上下文的一部分。系统需要在指令、当前输入、工具结果和历史记忆之间分配 token 与优先级。

### 15.4 与微调

微调适合稳定能力和风格，不适合频繁变化的个人事实。用户偏好和项目状态通常更适合外部记忆。

### 15.5 与 AI Agent

Agent 依靠记忆延续多步目标，但真正操作前仍要查询当前状态和权限。记忆提高连续性，不提供授权。

### 15.6 与提示注入防护

外部内容若能自动写入记忆，会形成持久化注入。记忆写入必须比普通生成拥有更严格的来源和安全检查。

## 16. 关键结论

1. 大语言模型不会因一次对话自动形成可管理的长期记忆，应用需要外部存储与检索机制。
2. 上下文窗口是当前可见信息，外部记忆负责跨会话保存，模型权重承载更稳定的能力模式。
3. 记忆可分为工作、情景、语义和程序等类型，治理方式不同。
4. 可靠记忆需要完整生命周期：提取、写入、存储、检索、使用、更新和遗忘。
5. 每条记忆应记录来源、时间、作用域、可信度和有效状态。
6. 向量相似度只能衡量语义接近，不能替代权限、时效和真实性判断。
7. 项目状态、权限和交易数据必须查询权威系统，不能依赖旧记忆。
8. 自动写入可能固化错误推断或提示注入，重要记忆应确认并可撤回。
9. 用户应能查看、更正和删除记忆，删除范围要覆盖摘要、向量和其他派生数据。
10. 评估记忆系统应关注长期任务效果、跨用户隔离和错误记忆造成的实际影响。

## 17. 延伸思考

- 什么样的用户偏好需要明确确认，什么样的偏好可以短期推断？
- 当两条记忆来自不同来源且互相冲突时，系统应如何选择？
- 如何让 Agent 解释“为什么这次使用了某条记忆”而不泄露其他信息？
- 记忆压缩到什么程度会开始损失决策所需的细节？
- 如果用户要求“忘记我”，系统应如何验证原文、摘要、向量和备份都被正确处理？
